# U12 decisions: leader lease, fencing, cursors

## Public surface (for U13 and every store unit)

| Type | Use |
|---|---|
| `Leader` (singleton, `IHostedService`, implements `ILeaderEpoch`) | `IsLeader`, `Current` (throws when not leader), `InstanceId`, `LeadershipLost` (token), `ReportFencingLost()` |
| `Leader.CommitFencedAsync(connection, commands, ct)` | The persist transaction of §c.7 step 3: `BEGIN` + one batch (`select rs_fence(epoch)` first, then the caller's commands), then a separate `COMMIT` |
| `Leader.FenceCommand(epoch)`, `Leader.IsFencingLost(e)` | Building blocks for code that runs its own fenced transaction |
| `CursorRepo.LoadAsync(room, cid, principal)` → `ClientCursor(Owner, LastQ)` | Dedupe step 1. `Owner` is `None`, `Caller` or `OtherPrincipal` (nack `forbidden`, S16) |
| `CursorRepo.Upsert(room, cid, principal, q)` | The cursor statement of the persist batch: `greatest(...)`, never rebinds another principal's cid |

`CommitFencedAsync` classifies failures for the actor (§c.7, R2):

- `FencingLostException` (inner `PostgresException` `RS001`): nothing committed. The leader has already marked itself lost and asked the host to stop, so the actor only stops.
- Any other exception from the batch: a definite failure before `COMMIT`; the transaction rolled back.
- `CommitOutcomeUnknownException`: the connection failed while `COMMIT` was in flight. A `PostgresException` from `COMMIT` (a deferred constraint such as the spotlight FK, R9) is the server's answer, so it is rethrown as is: the transaction rolled back for certain.
- `COMMIT` is never cancelled by the caller's token, because a cancelled `COMMIT` is an unknown outcome made on purpose.

## Startup and shutdown

1. `Leader.StartAsync` opens a dedicated owner connection (`Pooling=false`, `Keepalive=10`, application name `retroscope-lease`) and tries `pg_try_advisory_lock(0x52455452)` every second for the acquire window. A failure to connect counts as a failed attempt, so a database that is still starting is waited for within the same window.
2. It runs `Migrator.FromEmbeddedScripts().RunAsync(lease, db.AppPassword)` **on the lease connection**. The lease connection has to be the owner: on an empty database `retroscope_app` does not exist until the migrator creates it.
3. It bumps the epoch in one transaction on the lease connection: `pg_advisory_xact_lock(1381123153)`, then `update system_state … returning leader_epoch`.
4. A watchdog runs `select 1` (5 s command timeout) on the lease connection every 2 s.

Hosted services start before Kestrel listens, so the instance serves nothing until it is leader. If the window closes, `StartAsync` throws `LeaderUnavailableException`, the host fails to start and the process exits non-zero (134 on Unix, from the unhandled exception).

**Exiting non-zero after a loss.** `Program.cs` is frozen and returns 0 after `RunAsync`, so `Environment.ExitCode` cannot carry the failure. On a watchdog failure or `RS001` the leader cancels `LeadershipLost` and calls `StopApplication()`; the host then stops every hosted service (in reverse registration order, so actors and sockets stop before the lease is released, as §c.9 orders it), and `Leader.StopAsync` throws `LeadershipLostException`. `Host.StopAsync` rethrows it, `RunAsync` throws, and the process exits non-zero. A graceful stop (SIGTERM) releases the lock and exits 0. Both paths are tested against the real server binary.

## Decisions where the spec was silent

1. **`LEADER_ACQUIRE_SECONDS`** (default 60) sets the acquire window. It exists so the process test does not wait a minute; production leaves it unset.
2. **The cursor upsert never rebinds a cid.** `on conflict … do update … where client_cursors.principal_id = excluded.principal_id` makes another principal's upsert a no-op instead of an error. The actor refuses such a command at dedupe (`LoadAsync` returns `OtherPrincipal`) before it reaches the batch, so the upsert can only meet that case through a bug. Raising inside SQL would need a new function in `0001_init.sql` (U1's file).
3. **`CursorRepo` is registered in `Leader.AddServices`.** It is not a module (it has no hooks, so the scaffold test does not count it), and `Db.AddServices` belongs to U1.
4. **No `last_activity_at` bump here.** It is per room table, so it belongs to the stores (U21–U23) as one more command in the batch they pass to `CommitFencedAsync`.

## Verified: Npgsql pipelines `BEGIN` with the first batch (§12 row)

`FencedCommitTests.Begin_is_pipelined_with_the_batch_so_a_command_costs_two_round_trips` puts a TCP relay between Npgsql 10.0.3 and Postgres and counts client flights (everything the client sends before the server next answers). A fenced persist batch costs exactly two: the first write carries `Q`(BEGIN) followed by the batch's `P/B/D/E…S` messages, and the second is `Q`(COMMIT). Counting ReadyForQuery messages instead gives three, because the pipelined simple-query `BEGIN` gets its own ReadyForQuery in the same flight; that is not an extra round trip. **Verified.**

## Follow-ups for other units

- **U0 / `build.sh` owner:** the "chiseled image serves /healthz" step of `aot-smoke` (and so the AOT smoke job in CI) must give the container `DATABASE_URL` and `DATABASE_OWNER_URL`, for example by attaching it to the throwaway Postgres container's network (`--network container:$SMOKE_PG`, connecting to `127.0.0.1:5432`). Without a database the server now exits non-zero by design (§c.9: no leader, no traffic). U11's leader+DB `/healthz` condition would require this anyway.
- **U11:** `/healthz` can read `ILeaderEpoch.IsLeader`; `Leader.LeadershipLost` fires when the instance is about to stop.
- **U13:** use `CommitFencedAsync` for step 3 of the command pipeline and catch the three outcomes above; register actors' hosted service after `Leader.AddServices` runs (Program.cs already orders it so), so actors stop before the lease is released.
