# U9 decisions: team domain and authorization rules

U9 owns `src/Retroscope.Core/Team/**`, `src/Retroscope.Core/Authz/PolicyRules.cs`, `tests/authz-matrix.csv` and
`tests/Retroscope.Core.Tests/{Team,Authz}/**`.

## Authorization (`PolicyRules`)

1. **One subject, resolved per call.** `Evaluate` builds the caller's relationship to the resource from the
   arguments only: the team role comes from `IAccessView.RoleIn` and the password grant from
   `IAccessView.HasCurrentGrant` on every call (R12). Nothing is cached, so a demotion, a removal or a password
   change applies to the very next check.
2. **Fail closed first.** A null principal (unauthenticated HTTP), an `External` principal (imported Slack voter,
   never a live caller), `Deleted` or `TeamDeleted` deny every capability. A capability checked against a room
   kind it does not belong to (`PokerVote` on a board, `TeamDelete` on a session) is denied.
3. **Only users are team members.** A role the access view reports for a guest id is ignored.
4. **App admins get no room rights.** `IsAppAdmin` gates the `/api/admin/*` routes through `RoutePolicy`
   (U11/U27). Membership repair goes through the team actor. Nothing in §c.11 gives an app admin access to
   someone else's room.
5. **Room rules** (§c.11, §d, S12):
   * Poker: team sessions are for members; quick sessions are for any user or guest with the code. Observers may do
     everything except vote. Deleting a round and clearing all rounds need a team admin or owner (team) or any
     signed-in participant (quick). Deleting the session needs a team admin or owner (team) or the creator
     (quick, guest creators included, since `POST /api/poker` is guest-reachable). `PokerSubmitJiraPoints` needs a
     team session, Jira configured, membership, and `members_can_edit` or admin.
   * Boards: members always get in. Otherwise `link` lets anyone in, `password` needs a current grant (or, on a
     quick board only, being the creator), `team` lets nobody else in. Facilitating needs membership on team
     boards whatever the visibility, and a signed-in user on quick boards. Guests never facilitate. Endorsing
     and seeing the roster need a team board and membership. `RetroTimer` needs a signed-in user (§c.4). Archive,
     access changes and delete are `BoardManage`: team admin or owner on team boards, the creator on quick boards.
   * Team: members subscribe and update action items. Admins and the owner delete action items, manage members
     and settings, and configure Jira. Only the owner deletes the team. `JiraEditIssues` needs Jira configured and
     `members_can_edit` or admin.
6. **State gates with their own nack code are also denied by the policy.** An archived board denies every
   content capability (cards, votes, comments, readiness, focus, timer, facilitation, endorsements) but keeps
   `Subscribe`, the roster and the `BoardManage` capabilities, so it can be unarchived. Jira capabilities deny
   when Jira is not configured. The policy cannot return a nack code, so a decider that owes the client
   `board_archived` or `jira_not_configured` checks that state **before** calling `Policy.Can` (U7, U8, U26).
   That is an ordering rule for those codes only; authorization still comes from the policy.

## The matrix

* `tests/authz-matrix.csv` has one row per capability and resource of the capability's room kind (215 rows) and one
  column per viewer (`Y` allowed, `-` denied). The viewers are relationships to the resource: `anonymous`,
  `external`, `guest`, `user` (signed in, not a member), `app_admin`, `member`, `admin`, `owner`, `observer`
  (a member who observes), `creator`, `guest_creator`, `grant_holder`, `stale_grant` (unlocked the board, then the
  password changed mid-session) and `demoted` (admin when subscribing, member now). The resources cover quick and
  team sessions (with and without Jira, members-can-edit on and off), quick and team boards in each visibility,
  archived boards, deleted rooms, soft-deleted teams, and team rooms.
* The test checks every cell against `Policy.Can`, that every capability has an allow and a deny cell, that every
  resource of the capability's kind has a row, that everything is denied on other room kinds, and that the
  mid-session viewers answer like `admin`/`grant_holder` before the change (through the same access view) and like
  their own column after it.
* The CSV was generated from the implementation and then reviewed cell by cell against §c.11, §d and S12.
  `PolicyScenarioTests` states the named cases independently of the CSV. After an intended rule change,
  regenerate with `RS_UPDATE_AUTHZ_MATRIX=1 dotnet test tests/Retroscope.Core.Tests --filter Category=Authz`
  and review the diff.

## Team domain (`Core/Team`)

1. **`TeamInput`, not `TeamCommand`, is the decider's command type.** U2 decision 3 says internal commands may
   derive from `TeamCommand`, but U2's `Every_concrete_payload_type_has_exactly_one_kind` test scans the whole
   Core assembly and fails on any concrete `Command` that is not in the catalog. So `TeamDecider` implements
   `IRoomDomain<TeamState, TeamInput, TeamEvent>`. A client command is wrapped with `TeamInput.From(command)`.
   Internal posts (`ActionItemCreated`, `SyncActionText`, `SourceCardDeleted`, `ActionItemCommentsChanged`,
   `BoardsChanged`, `PokerChanged`, `MemberAdded`, `MemberRoleSet`, `MemberRemoved`, `SettingsChanged`,
   `TeamDeleted`) are their own `TeamInput` cases with no viewer. U7 and U8 face the same test (see follow-ups).
2. **Events are self-contained.** The ring keeps domain events and re-projects them for replay later, when the state
   has moved on. Action-item events therefore carry the whole resulting `ActionItemInfo`, and member events carry
   the whole roster after the change, so `TeamProjection.ToWire(evt)` needs no state. The store (U23) still writes
   only the columns each event names (R24): assign changes `assigned_to`, done changes `done_at`/`done_by`, text
   sync changes `text`/`source_version` (guard it in SQL with `source_version < $v` too), and `ActionItemAdded`
   and `ActionItemSourceDetached` write nothing (the board actor's transaction already did).
3. **Action-item rules.** Assign and done need `TeamUpdateActionItem`; delete needs `TeamDeleteActionItem`. An
   unknown item is `not_found`. The assignee must be a member **now** (through `IAccessView`, not the projected
   roster), else `invalid`. Assign and done are set semantics: the current value is a `NoOp`. Done stamps
   `doneAt = now` and `doneBy = caller`; undone clears both.
4. **Idempotent create.** `ActionItemCreated` is a `NoOp` when the id is already held, and also when another item
   already holds the same source card (the unique index on `source_card_id` would have refused that row anyway).
5. **Monotonic text sync.** `SyncActionText` is keyed by the source card (as `ITeamNotices.ActionItemTextChanged`
   is) and applies only when `cardVersion > SourceVersion`. A card the state does not hold (unknown, or closed
   more than 30 days ago and not loaded) is a `NoOp`. The load-time repair query (§c.2, U23) catches it up.
6. **Membership.** `MemberAdded` for an existing member is a `NoOp` and keeps their role: accepting a member link
   must not demote an admin. Role set and removal of a non-member are `NoOp`s. Roster order is owner, admins,
   members, then `NaturalCompare` on the name.
7. **Settings** events carry only the fields whose value changed; nothing changed is a `NoOp`.
8. **`TeamDeleted`** marks the live state deleted so every later command is `forbidden` through the policy. It
   has no wire form: the access-change path kicks subscribers.
9. **Snapshot** lists open items plus items done within the last 30 days (`doneAt >= now − 30 d`), newest first.

## Follow-ups for other units

* **U2:** either let `ProtocolCatalogTests.Every_concrete_payload_type_has_exactly_one_kind` ignore types outside
  `Retroscope.Core.Protocol`, or correct decision 3. Until then domain-internal commands cannot derive from
  `PokerCommand`/`RetroCommand`/`TeamCommand` (U7, U8: use an input wrapper as `TeamInput` does).
* **U2 / U24:** `TeamManageMembers` is admin-or-owner, but §d makes role changes, removing an admin and transferring
  ownership owner-only, and lets any member leave. There is no capability for those, so U24 must compare
  `RoleIn(...) == Owner` itself or ask U2 for a `TeamManageAdmins` capability, which U9 would then add to the
  rules and the matrix.
* **U2 / U24:** endorsement types and board templates are team-actor tables (§c.2), but there is no wire event for a
  change to them, so `Core/Team` has no input for them yet.
* **U7, U8, U26:** check `Archived` / `JiraConfigured` before `Policy.Can` when the nack must be `board_archived` or
  `jira_not_configured` (decision 6 above).
* **U23:** build `ResourceFacts` for a team room with `TeamDecider.Facts(state)`, and translate `ITeamNotices` calls
  into the matching `TeamInput` cases.

## Changes from UF3

* **`TeamManageAdmins`** (owner only): changing a role, removing an admin and transferring ownership (§d).
  `TeamManageMembers` stays admin-or-owner for invites and removing plain members. **U24:** use it instead of
  comparing `RoleIn(...) == Owner`. Self-leave is not a capability: the handler allows a member to remove themselves.
* **Board rules delegate to `RetroRoles`** (U8): `RetroFacilitate` and `RetroTimer` → `IsFacilitator`;
  `RetroEndorse` and `RetroViewRoster` → `IsMember`; `RetroReady` and `RetroFocus` → `MayPace` (members only on
  team boards). The matrix changed in those rows only: every non-member viewer that could open the board lost
  `RetroReady`, `RetroFocus` and `RetroTimer` on `board_team_link` and `board_team_password`.
* **Team state prunes** items closed more than 30 days ago whenever an event is applied. Team events carry the
  decision time (`TeamEvent.At`, stamped by `TeamDecider.Decide`); an event built elsewhere has the default time and
  prunes nothing.
