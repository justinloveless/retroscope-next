## Decisions where the spec was silent or did not fit

1. **"Decimal `jira_points`".** The old app never stored the points it wrote to Jira (no source column holds them;
   `average_points` is the plurality winner written at reveal, not a Jira value). So `jira_points`, `jira_points_at`
   and `jira_points_by` stay null for every imported round. `average_points` is `numeric` and is read as `decimal`:
   legacy fractional values (pre-history averages such as 2.5) compare exactly with the recomputed winner, and a
   mismatch is reported with the decimal value intact. Our winner is kept.
2. **Which teams exist.** The stage reads `select id from teams` in the main transaction (U39 wrote them). A session
   whose team was not imported is skipped (`team_missing`) with its rounds counted as `orphan`.
3. **Voter keys.** A UUID key that is an imported user maps to the kept user (following duplicate-email merges); any
   other UUID key becomes `v5(guest:<lower-case uuid>)`, so a browser that stored the id in another case is one
   guest. `slack_*` keys become `v5(slack:<key>)` external principals named "Slack user". Keys that are neither a
   UUID nor `slack_*` are treated as guest keys too (`v5(guest:key)`) instead of being dropped. A guest is named by
   the latest name seen for its key across all rounds (by round `created_at`), scrubbed; a guest that is only an
   observer is named `Guest`. Principals are created only when a kept vote or an observer row references them.
4. **Abstentions in voting rounds.** "Only locked deck-valid entries" also keeps a locked `-1`: the old client's
   abstain sets `locked: true, points: -1` (`context.tsx:1396`), so it is an explicit choice, not a synthetic row.
   Revealed rounds turn unlocked, off-deck and missing points into abstentions. Every imported vote is `locked`.
5. **Observers.** `observer_ids` resolve like voter keys (users first, else `v5(guest:id)`). In voting rounds an
   observer's selection is dropped, because the domain never holds an observer's vote on a voting round (U7
   decision 9); revealed rounds keep it as history.
6. **Two keys, one principal.** When a merged duplicate account and its kept account both voted in a round (or two
   keys otherwise resolve to one principal), the entry whose key is the kept id wins, else the smallest key. The
   selections map has no per-entry timestamp, so "keep the newest" has nothing to compare.
7. **Renumbering.** Rounds numbered below 1 (the Slack bot's sessions start at 0) are renumbered with the losing
   duplicates: all of them above the session's maximum, in `created_at` order (then id). The kept duplicate is the
   latest `created_at` (then the largest id).
8. **Sort keys** are the 0-based position in `(sort_order, number)` order, matching Core's `RoundCreated.SortKey`
   (an index into `Order`). `number` is the renumbered value, so the order is total.
9. **Pointer.** `current_round_id` is the round whose final number equals `current_round_number`; if there is none
   (pending, renumbered or a Slack session's 0) it is the highest-numbered round, the domain's pointer repair rule
   (U7 decision 6), counted as `poker.pointerRepaired`. No rounds: null and `next_round_number = 1`.
10. **Codes.** A `room_id` that fails the target's `^[A-Za-z0-9-]{4,36}$`, or that an earlier session (by
    `created_at`) already took exactly, falls back to `id::text` and is reported. The fake source has a unique
    `room_id` constraint, but the live one is unverified, so the duplicate path is tested with it dropped.
11. **Ticket keys** go through `TicketKeys.TryNormalize` with no prefix: a bare number (a key typed without its
    project) is invalid and nulled, since the team prefix of the time is unknown. Parent keys follow the same rule.
12. **Other columns.** `created_by` is null (the source has no creator). `follow_spotlight` takes the target default
    (`spotlight_follow_enabled` is an omitted ephemeral column). `revealed_at = completed_at`, `revealed_by` null.
    `poker_votes.updated_at = completed_at`. `presence_enabled` null → true; `auto_reveal_enabled` and `is_active`
    are copied.

## Tests

`tests/Retroscope.Importer.Tests/Poker/` runs the real runner with `MinimalIdentityStage` (order 100) standing in
for U39: kept users become principals and users, source teams become bare teams. The integrator can drop it once
U39's stages are merged and the tests use them instead.

## Amendments (UF8)

- **Code fallback (decision 10).** The fallback is the session id, then the id without hyphens (`N` format, 32
  characters), then that plus `-<n>`. All of them pass the code check, so a `room_id` equal to another session's id
  text no longer throws on the second insert into the code map. The replaced session is reported as `duplicate`.
- **`average_points` is read as `decimal?`.** The fake source has it `not null default 0`, but the live schema is
  unverified, so a null is not read as 0: it is counted (`poker.nullAveragePoints`), listed
  (`pokerNullAveragePoints`, round ids), never compared with the recomputed winner, and does not count as "had a
  winner" in the legacy reveal rule.
- **Selections the parser refuses** (jsonb nested beyond 64 levels) count as `poker.droppedSelections.malformed`, like
  a non-object value, instead of aborting the run.
- **Guest ids (decision 3)** come from `SyntheticIds.Guest(Guid)`, which hashes the lower-case `D` form. The retro
  stage uses the same overload for a UUID-shaped `session_id`, so a browser that used both apps is one guest.
