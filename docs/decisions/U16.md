# U16 decisions: auth core

U16 owns `Server/Auth/{Sessions,Guests,Passwords,AccountClaims}.cs`, `Server/Endpoints/{AuthEndpoints,MeEndpoints,GuestEndpoints}.cs`,
`Server/Data/Repos/{Users,Sessions,Guests}Repo.cs`, `Server/Json/AuthJsonContext.cs` (transferred per U0 decision 3) and its
tests in `tests/Retroscope.Integration.Tests/Auth/**`.

## Contracts later units rely on

| Type | Use |
|---|---|
| `Sessions.SignInAsync(context, principal, emailVerified, method, ct)` | Starts a session and sets `__Host-rs_sid`. A session the request already carries is revoked first, so every sign-in rotates the token. U17 (magic link) and U18 (OIDC) call it after proving ownership |
| `Sessions.RevokeAsync / RevokeAllAsync(user, keep, ct)` | Delete, evict from the cache, and call `IConnectionRevoker.RevokeAuthSession` for each session. U27 (disable, privilege change) and U17 (reset consume) use them |
| `Sessions.Revoked(hashes)` | For sessions deleted inside another transaction |
| `Sessions.EvictUser(user)` | After any change to a user's name, avatar, admin flag or verification, so the next request sees it (U18, U20, U27) |
| `Sessions.PublicId(idHash)` | The session's public `Guid` (below). It is `Caller.AuthSessionId` and the id `IConnectionRevoker` receives |
| `AccountClaims.ClaimAsync(user, OwnershipProof, ct)` | The takeover rule (§e). True when the account was unverified and is now verified with no password and no sessions; false for a verified account. The caller then signs the prover in |
| `IAccountMail` | Implemented by U17: `SignedUpAsync` (verification link), `AlreadyRegisteredAsync`, `LoginCappedAsync` (unlock link). `NoAccountMail` is registered with `TryAdd` until then. U17 calls `EmailBudget.TryReserve` itself |
| `HashGate.RunAsync(work, ct)` / `HashGate.BusyResult()` | Every bcrypt hash or verify, wherever it runs (U17 reset consume, U25 board passwords) |
| `PasswordRules.Check(password)` | The signup/change rule (10–72 bytes, not common). U17's reset consume uses it |
| `UsersRepo.DisplayNameSql` | `coalesce(u.nickname, nullif(u.full_name, ''), 'Player')` over `users u`: the one display-name rule for every roster or author query |
| `UsersRepo.Audit(action, actor, target, meta, now)` | An `audit_log` batch command; `AuthAudit.EmailHmac(email)` for `email_hmac` |
| `MeBuilder` | `/api/me` and the boot JSON's `me` |

## Decisions where the spec was silent or did not fit

1. **Session public id.** `sessions` has only `id_hash` as its key, but `Caller.AuthSessionId` and
   `IConnectionRevoker.RevokeAuthSession` take a `Guid`. The public id is the first 16 bytes of the token hash. It reveals
   nothing about the token, needs no schema change, and `/api/me/sessions/{id}` uses it too.
2. **Request DTOs carry `[JsonUnmappedMemberHandling(Disallow)]` on the type.** The context-level
   `UnmappedMemberHandling = Disallow` in `AuthJsonContext` does not apply to minimal API binding: `Program.cs` chains
   the contexts into the host's `JsonSerializerOptions`, and those options allow unmapped members, so `{"isAdmin":true}`
   was accepted. A test caught it. **Every HTTP unit must put the attribute on its request types**; the route-inventory
   test could check the `JsonTypeInfo` of each endpoint's body parameter (U11).
3. **Backoff keys.** The account is the normalized email, so unknown addresses are throttled exactly like real ones
   (no oracle). The IP part is `ClientIp.AuditPrefix` (/24, /48), as the U11 follow-up asks; §d's "/24 or /64" for
   login is read as the audit prefix. The schedule: from the 5th failure the (account, prefix) pair waits 1 min, then 2, 4,
   8, and 15 at most. A pair with no failure for 30 minutes starts again. A success clears the pair.
4. **Account cap.** 50 failed logins per account per hour from all addresses together (a token bucket). Past it, password
   login for that account answers 429 from every address until the bucket refills, and `IAccountMail.LoginCappedAsync`
   is called once per capped episode (only when the account exists). There is no `unlock` purpose in `auth_tokens`, so
   U17 should send a magic sign-in link: signing in is the unlock. Both limits are in memory; one process (§c.9).
5. **Login responses.** Success: 200 with the `/api/me` body. Wrong password, unknown email, disabled account and an
   account without a password all answer the same 401 `invalid_credentials`, after the same verify cost (`DummyVerify`).
   Backoff or cap: 429 `rate_limited` with `Retry-After`. Gate full: 503 `busy`, `Retry-After: 2`.
6. **Signup** always answers 202 with no cookie; the client logs in next with the same credentials. Signing in from signup
   would answer an existing address differently. The password is hashed before the lookup, so both paths cost the same.
7. **Password change** (`PUT /api/me/password`): a wrong `current` is 403 `wrong_password`; a first password without a
   Google, Entra or magic-link session younger than 10 minutes is 403 `reauth_required`. On success **every** session is
   revoked (sockets closed) and this browser gets a new session with the same auth method. That is "revokes other
   sessions" plus "password change rotates the token" (§e).
8. **Guests.** `POST /api/guest` with a live guest cookie renames that guest (200) instead of minting another, so the
   browser keeps its seats; a signed-in user gets 409 `signed_in`. `PATCH` by a user is 403 `not_guest`. Names are
   1–40 characters after trimming with no control characters, lone surrogates or bidi overrides, and nothing with an `@`
   between two non-space characters (S21). The guest token slides at most daily and the cookie is re-sent when it does.
9. **Display name.** `nickname`, else `full_name`, else `Player` (the original roster fallback,
   `usePokerSession.ts:155-158`). Never the email (gaps: display-name leakage).
10. **Common-password list.** §d says "the embedded top-10k list". Only 51 entries of SecLists
    `Common-Credentials/10k-most-common.txt` (MIT, commit 913b327, sha256 `68782d6a…c50fdcce`) are 10 or more characters,
    and the length rule already refuses the other 9,950, so the 51 are a literal set in `Passwords.cs` (case-insensitive).
    No resource file or csproj change is needed. A longer list filtered to ≥ 10 characters would refuse more; that is a
    product choice, not done here.
11. **`/api/me` scope.** U16 maps `GET/PATCH /api/me`, `PUT /api/me/password`, `GET /api/me/sessions` and
    `DELETE /api/me/sessions/{id}`. `/api/me/avatar` belongs with the blob code (U20), `/api/me/mentions*` with U25,
    `/api/me/endorsements` with U24 and `/api/me/identities/{provider}/link` with U18. `unreadMentions` counts mentions
    newer than `mentions_seen_at` on boards the user can still subscribe to (board and team not deleted; member, `link`,
    or `password` with a current grant or as the quick board's creator), mirroring U9's rules in SQL.
12. **Magic link, reset and verify routes** (`/api/auth/{magic,reset,verify}/*`) are U17's; they need its tokens and
    outbox, and U17 can map them from `EmailModule.Map`. U16 provides the session, claim and password pieces above.
13. **`me` in the boot JSON** is `null` when signed out, else the `/api/me` body; `theme` is the user's preference.
14. **Test database connections.** Each test host clears the owner connection pool of its database on disposal. Without
    it, ~45 extra test databases pushed the run past Postgres's 100 connections ("too many clients") until UF4's fixture
    change lands.

## Measured: bcrypt throughput (§e: "U16 measures hashes/s")

`HashGateEndpointTests.Bcrypt_throughput_is_recorded` prints it on every run. On the development machine (Apple silicon,
arm64, Debug build, one thread) BCrypt.Net-Next at cost 10 does **about 12 hashes/s** (≈ 85 ms each), so the width-1 gate
admits about 12 logins per second and a full 50-deep queue drains in about 4 s, past the 2 s wait. **The figure on the
target VPS is unverified**: there is no access to it from this session. U43 records it there with the same test.

## Not done here

- The `/invite/[redacted]` request-log rule (§e, U11 "not done") needs request logging, which does not exist yet (U43).
- Renaming a guest or user does not update live rooms' presence; that needs the actors (U13, U21–U23).

## Amendment (UF7): signup parity

Signup on a taken address no longer takes an extra `FindIdAsync` round trip. One statement (`AuthEndpoints.SignupSql`)
looks the address up, inserts the principal and the user only when it is free, and returns either the new id or the
owner's id. In one run on the test database (Docker on macOS) a read-only taken path still answered about 55 ms faster
than a new address, because only the new address committed a write and waited for the WAL flush. So both outcomes
write an audit row in the same statement: `auth.signup` (actor and target the new user) or `auth.signup.taken` (target
the owner), with `email_hmac` and the IP audit prefix, never the address. Both paths now run one command and one
durable commit. Only a concurrent signup of the same address, which fails the unique constraint, falls back to
`FindIdAsync`. The SQL lives in `AuthEndpoints.cs` because `UsersRepo.cs` was not part of UF7's paths;
`UsersRepo.CreateAsync` is unchanged for its other callers. `AuthCore/SignupParityTests` checks that both outcomes run
the same database commands (Npgsql's activity source) and that their median times are within 0.6x of each other, like
the login test.
