# U28 decisions: net layer (socket, outbox, RoomStore)

U28 owns `web/src/net/{socket,outbox,room}.js` and `tests/web-unit/net/**`.

## Contracts later units rely on

1. **Wiring.** `createSocket({pid, onNack})` (U29's entry, with `pid` = `boot.me?.pid`) creates the outbox
   and the clock itself; `socket.start()` opens the connection and `socket.room(key, model, {onNack})`
   returns that room's RoomStore. A room joined before the hello goes out rides in `hello.subs`; one
   joined later sends `sub` at once. `socket.leave(room)` unsubscribes once the room's outbox entries are
   answered, so leaving a page never strands a command. Every dependency (`WebSocketImpl`, `setTimer`,
   `now`, `random`, `doc`, `win`, `storage`, `channel`, `uuid`) is injectable for tests.
2. **The model contract** (U31 `poker/model.js`, U34 `retro/model.js`, U30 team): `snapshot(d, o) → state`,
   `apply(state, {k, d}) → state` for one wire event, and optionally `optimistic(state, k, d) → state`,
   used for entries restored from sessionStorage after a reload (their `apply` closures are gone).
   States should be treated as immutable; the view is `pending.reduce(apply, confirmed)`, computed lazily.
3. **`room.send(k, d, options)`** returns the outbox entry (`{r, q, k, d, pid, sentAt, sent}`) or null when
   the room was kicked or the outbox is full. Options:
   - `apply(state) → state`: the optimistic intent.
   - `rebase(view, nack) → d | null` and `applyFor(d)`: for `stale` on `poker.round.reorder` and
     `retro.column.reorder`; the room resends the result once, as a new entry.
   - `onNack(nack) → true when handled`: the card-edit merge prompt, composer draft restore (R21) and the
     "Take spotlight?" confirm, which resends `poker.spotlight.take` with `force:true` itself.
   Unhandled final nacks go to the room's `onNack` (screens toast them). `nack` is
   `{code, msg, d, k, sent}`, where `sent` is the command payload. A full outbox reports
   `{code:'outbox_full'}` ("offline too long").
4. **Stale policy** is the `STALE` table in `room.js`: `rebase` for the two reorders, `silent` for
   `setTicket`, `focus.set`, `settings.update`, `config.update` and `board.rename` (§g.4). Every other
   `stale` (card edit included) reaches the handlers.
5. **Reading state.** `room.view` (confirmed + pending), `room.confirmed`, `room.pending()` (entries, for the
   1.5 s spinner: compare `sentAt`), `room.synced`, `room.kicked` (kick code or null), `room.extras`
   (`x` frames as `extras[k][d.key]`), and `room.select(fn, eq, listener)` from U10's `createHub`.
   `room.seed({e, s, d, o})` paints the boot snapshot before the socket is up.
6. **`socket.status`** is a store of `{state, offlineSince, code}` with state `connecting`, `open`,
   `waiting` or `closed`; the "Reconnecting…" banner shows when `now − offlineSince > 10 s`. `closed` with
   `code` 4401 or 4403 is terminal (sign in again). `socket.me` is `welcome.me`; `socket.clock` is
   U10's clock, seeded by `welcome.n` and sampled by pongs.

## Decisions where the spec was silent or did not fit

1. **Retryable nacks renumber.** §g.4 says a retryable nack keeps the entry and resends it. Resending with
   the same `q` is unsafe: if a later command of the same room committed in between (a `rate_limited`
   q=5 followed by an accepted q=6), the cursor is past 5 and the resend is acked `dup` without being
   applied. The server never applied a nacked command, so the entry is resent with a fresh `q`. Resends
   after a reconnect keep their `q`, as §g.4 requires, because there the command may have committed.
   Until the retry fires, new commands of that room queue instead of going out, so the resend still
   precedes them on the wire and `q` strictly increases there (§c.3); otherwise a command issued during
   the backoff would commit first and turn the resend into a `dup` all the same.
2. **Unsent entries renumber at sync.** `cseq = max(cseq, lastQ)` happens on every snap/replay (R4). An
   entry that was queued before that (offline, or right after a reload whose storage regressed) but never
   transmitted may hold a `q ≤ lastQ`; it gets a fresh `q` at sync. Entries that were transmitted keep
   theirs, so a commit whose ack was lost still comes back `dup`. Commands are only transmitted once the
   room has synced, never before.
3. **cid_reuse reconnects.** The cid is bound to the connection by `hello`, so "mint a new cid and resend
   with new `q`s" (§c.6) means: remint, renumber every entry, reconnect at once. The nacked entry is kept
   (the other tab's command was the one applied).
4. **4409 keeps `q`s.** §g.4: mint a new cid, keep the outbox, reconnect (with the normal backoff, so a
   server that keeps refusing is not hammered). Under the new cid the cursor starts at 0, so nothing needs
   renumbering.
5. **The bye frame drives the restart, not the close code.** On `bye` the client closes the socket itself
   and reconnects after exactly `retryMs`; neither the server's close, `online` nor `visibilitychange`
   shortens that wait (the server spreads reconnects on purpose). WebKit reports 1012 as 1005 (U48), and a
   close without a bye is an ordinary drop either way: jittered backoff. Only 4401 and 4403 stop the
   socket.
6. **The watchdog only runs while visible.** JavaScript cannot see the server's protocol PING/PONG, and a
   hidden tab sends no clock pings, so 90 s of silence in a hidden idle room proves nothing and would
   reconnect every 90 s. Becoming visible pings at once and re-arms it.
7. **Duplicate-tab check timing.** A tab that restored a cid from sessionStorage asks `BroadcastChannel('rs')`
   and waits 100 ms for a twin to answer before `hello` (the socket opens in parallel, so this rarely
   costs anything). A fresh tab has nothing to check. Tabs that are still checking do not answer, so two
   copies booting together fall back to the server's 4409.
8. **Principal change.** The outbox is bound to `boot.me.pid` before the first hello. If `welcome.me.pid`
   still differs (cookie changed in another tab), the outbox is cleared, a new cid minted and the socket
   reconnects at once, because the hello went out under the old cid.
9. **Storage failure.** If sessionStorage cannot be read, the tab runs in memory with a fresh cid. If a
   write fails later, the tab switches to memory, keeps its entries and removes `rs.cid`/`rs.outbox`, so a
   reload starts clean instead of resending a half-written outbox under a stale cid.
10. **Acks during a resync are deferred** until the replay or snapshot arrives, so an acked intent does not
    disappear before the tx that confirms it is applied. Kicked rooms drop their outbox entries (they can
    never be delivered) and are not resumed in later hellos.
11. **Retry backoff** for retryable nacks is the exact `250 ms × 2ⁿ`, capped at 5 s (§g.4 gives no jitter);
    it resets on the next ack. Reconnect backoff is full jitter `[0, min(10 s, 250 ms × 2ⁿ))`, reset after
    30 s connected.

## Verification

- `node --test tests/web-unit/net` (Node 20.19.1): 70 tests. `fake-server.test.js` runs the real socket
  against `tests/web-fake-server` over a TCP WebSocket (commit, bye + dup resend, gap + replay, 4409,
  scripted `cid_reuse` nack) with the fake's protocol validator on every client frame. The fake can
  already script a `cid_reuse` nack through `onCommand`, so nothing is pending on UF5.
- Removing the `lastQ` sync from `room.js` fails the `cseq = max(cseq, lastQ)` test.

## UF6 additions

12. **A retry never reverses a newer intent.** Every outbox entry carries `key`, its supersede key from
    `web/src/net/supersede.js` (`SUPERSEDE`, one row per catalog command kind, kept complete by
    `supersede.test.js`): the kind, or a shared group, plus the target members, e.g. `poker.vote.set:<roundId>`,
    `retro.card.edit:<cardId>`, `retro.vote.set:<cardId>`. Adding an entry marks every earlier entry of the room
    with the same key `superseded`; a retryable nack marks the entry `retry`. Both flags are persisted. A
    retryable nack on a superseded entry drops it at once, and a retry that a newer entry superseded during its
    backoff (or before a reload) is dropped instead of being resent. Since the mark is set when the newer entry is
    created, "pending, in flight or acked" needs no extra bookkeeping. A dropped entry is not reported: the newer
    entry carries the user's intent. Creates have no key and always retry. Abstain shares the vote key (both write
    the caller's seat) and `round.end` shares `round.activate`'s (both set the same flag). Overwrites whose
    precondition names the replaced value (`from`: stage, focus, timers) or that patch only some fields
    (`settings.update`, `column.update`, `config.update`, `timer.setFlags`) have no key, because the newer command
    may depend on the older one having applied, and dropping the older one would lose both.
13. **cid_reuse renumbering is made harmless on the server.** A create whose id already exists with the same
    payload is a resend of a command that committed under the old cid; the Core deciders return `NoOp`, so the
    actor acks it (without `dup`, which the client treats the same) and nothing is applied twice. The Core rules
    are listed in `docs/decisions/UF6.md`.
