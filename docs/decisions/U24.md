# U24 decisions: team HTTP

U24 owns `Server/Endpoints/{TeamsEndpoints,InvitesEndpoints,TemplatesEndpoints,EndorsementsEndpoints,DashboardEndpoints}.cs`,
`Server/Data/Repos/{Teams,Invites,Templates,Endorsements,Activity}Repo.cs`, `Server/Json/TeamHttpJsonContext.cs`
(transferred per U0 decision 3) and its tests in `tests/Retroscope.Integration.Tests/TeamHttp/**` (`Category=TeamHttp`;
§k names no test path, so the U13/U23 precedent applies).

## Contracts other units can use

| Type | Use |
|---|---|
| `TeamAccess.CheckAsync(context, teamId, capability)` | Finishes a team route's authorization: 404 `not_found` for a missing or deleted team and for non-members (the same body), 403 `forbidden` for a member without the capability. U25/U26 may reuse it for `/api/teams/{id}/…` routes |
| `TeamActors` | `AskAsync` to the team actor, `WarmAsync` before an HTTP write to `teams`, `Failure(context, result)` maps an `AskResult` to a response |
| `ActivityRepo.TouchAsync(user, kind, id)` | `recent_activity` upsert, debounced in memory to once per 5 minutes per (user, entity) (§c.5) |
| `TeamsRepo.Audit(action, actor, team, target, meta, now)` | An `audit_log` row with `team_id` set |
| `ListCursor` | The `<unix ms>.<uuid>` keyset cursor of the action-item list |

## Decisions where the spec was silent or did not fit

1. **Which routes are U24's.** §k gives U24 the team, invite, template, endorsement and dashboard endpoint files. Of the
   `/api/teams/{id}/…` routes in §d, U24 maps everything except `boards`, `poker-sessions` and the action-item
   comments (U25 owns `RetroLists`, `PokerLists` and `ActionItemComments`) and `jira/**` (U26). `GET …/action-items`
   is U24's (it lives in `TeamsEndpoints`; no other unit's check names it), and so are `GET /api/me/endorsements` (U16
   decision 11) and the leaderboard.
2. **Response shapes** follow `docs/decisions/U30.md` and `U29.md`, which the screens and the demo server already use:
   * `GET /api/teams` → `[{id, name, description?, role, favorite}]`; `POST /api/teams` → 201 `{id}`.
   * `GET /api/teams/{id}` → U30's shape. `jira` is `{configured:false, status:'ok', membersCanEdit:true}` without a
     config, else the stored `status` as it is (`needs_test` and `unreachable` included; U26 owns what they mean).
     `counts.boards` counts boards that are neither deleted nor archived. `PATCH` answers the same shape.
   * `GET …/members` → a bare array of `MemberInfo` (`{pid, name, role, avatar?}`) in roster order, like the demo; it
     is not paged and never carries an email.
   * `GET …/invites`, `…/templates`, `…/endorsement-types` → `{items, nextCursor:null}` (unpaged; small lists).
     `GET …/action-items` is keyset-paged (`limit` 1–100, default 50).
   * `GET /api/me/endorsements` → `[{emoji, typeName, fromName, teamName, createdAt}]`, newest 100, deleted teams left out.
   * `GET /api/dashboard` → `{teams, favorites:[{id, name, lastAt}], boards:[{id, code, title, teamName?, lastAt}],
     sessions:[{id, code, teamId?, teamName?, lastAt}]}`.
   * `POST /api/invites/accept` → `{teamId}`; `POST /api/invites/preview` → `{teamName, kind, expired}`.
3. **Errors.** Owner-protection refusals (changing the owner's role, removing or self-removing the owner) are 409
   `owner`. An ask the team actor could not take is 503 `unavailable` with `Retry-After: 1`. Invite errors use the
   codes `screens/invite.js` maps: unknown token, an email invite used by someone else, or a deleted team → 404
   `not_found`; revoked → 410 `revoked`; expired → 410 `expired` (preview answers `expired:true` instead); wrong or
   unverified address → 403 `email_mismatch` / `email_unverified`.
4. **Admin invites.** §d lets admins send email invites with a role, but role changes are owner-only
   (`TeamManageAdmins`, UF3). An email invite with `role:'admin'` therefore needs the owner; an admin inviting an admin
   gets 403. Link invites are always `member` (S19); asking for another role is 400.
5. **Membership changes go through the team actor** (`AskAsync`, never `Post`, U23): accept (`MemberAdded`), role
   change, removal and transfer. The actor writes `team_members`, publishes the roster to the cache and fans out
   `AccessChanged` (so a removed member is kicked). Audit rows are written by the handler after an accepted ask. A
   transfer demotes the owner, then promotes the target (the one-owner index is not deferrable); if the promotion does
   not go through, the old owner is promoted back.
6. **Email invite acceptance.** The invite is claimed with one conditional `UPDATE` (single use, race-free) before the
   ask, and given back if the ask fails. A used email invite is dead for everyone: replaying it never asks the team
   actor, and only answers `{teamId}` (idempotent retry) when the caller is still a member; a member since removed gets
   404, even if the invite was later revoked or expired. `MemberAdded` for a member is a no-op, so accepting never
   changes an existing role.
7. **Invite mail** goes through `EmailBudget.TryReserve(email, ip, sender: inviter)`, then the invite row, the audit row
   and the outbox row commit in one transaction, and `Outbox.Kick()` runs after the commit (U17). Over budget the
   invite is still created and the mail is dropped.
   Email invites last 7 days; link invites 1–30 days (default 7).
8. **`token_box`** is `Keyring.Seal(InviteBox, UTF-8 token, AAD = invite id's 16 bytes, RFC 4122 order)`, the layout
   the importer writes (U39 decision 2); a test seals with that layout and lists it. A box that does not open lists the
   invite without a `url`.
9. **Settings fan-out.** `PATCH /api/teams/{id}` writes `teams` itself (U9: the handler writes settings) and then asks
   `SettingsChanged`. A team room that loads *after* the write sees no change and fans nothing out, so the handler
   first loads the room (`WarmAsync`), then writes, then asks.
10. **Soft delete kicks.** The handler sets `deleted_at`, asks `TeamDeleted` (the team room kicks its subscribers
    `deleted`), publishes an **empty roster** for the team to the membership cache, and calls `AccessChanged` on every
    session and board of the team. Poker and board states do not know their team was deleted (no input for it), but
    with no members every team session and every `team`-visibility board refuses all former subscribers
    (`access_revoked`). Nobody is a member of a deleted team, so the empty roster is true and the team actor never
    reloads a deleted team. The cache entry is the only guard, though: `MembershipCache.LoadAsync` (U23) reads
    `team_members` without looking at `teams.deleted_at`, so after a restart or a `Forget` the old roster would be read
    back for the rooms' access checks (see the U23/UF9 follow-up).
11. **Templates and endorsement types are written over HTTP.** §c.2 lists them as team-actor tables, but there is no
    `TeamInput` or wire event for them (U9 follow-up), so the handlers write the rows. The live team room's endorsement
    types (snapshot only) catch up when it next loads.
12. **Text rules.** Names and titles are one trimmed line of plain text (`GuestNames.IsPlainText`: no control or bidi
    characters, no lone surrogates); descriptions may hold line breaks. Lengths count code points, as `char_length`
    does. Point descriptions accept deck keys only, drop empty texts and replace the whole map.
13. **Seeds.** A new team gets the original's default template ("Default": Good/green, Bad/red, Kudos/blue, Action
    Items/yellow as the action column; `BoardTemplatesSettings.tsx`) and its three default endorsement types (Problem
    Solver 🧩, Team Player 🤝, Innovator 💡; `seed_default_endorsement_types`), in the creating transaction with the
    owner row (create in place, §c.2) and a `team.create` audit row.
14. **Recent activity.** `GET /api/teams/{id}` touches the team. The dashboard lists the user's teams (by last visit,
    else join time), favorites, and the five most recent boards and sessions among those in `recent_activity` and those
    the user created, re-checked with the board/session subscribe rules in SQL and leaving out archived boards (as the
    demo does).
15. **Audit actions:** `team.create`, `team.settings`, `team.delete`, `team.role.set`, `team.member.remove`,
    `team.member.leave`, `team.member.add` (invite accept; meta: invite id, kind, role), `team.owner.transfer`,
    `team.invite.create` (meta: kind, role), `team.invite.revoke`. Never addresses or tokens. These are the role,
    membership and team lifecycle writes §d asks for; template, endorsement-type and favorite writes are not audited.

## Follow-ups for other units

- **UF9 (transport):** call `ActivityRepo.TouchAsync(user, Board|Poker, id)` on a signed-in user's first `sub` (§c.5);
  until then the dashboard's boards and sessions come from what users created.
- **UF9 / U8 (rooms):** poker and board rooms should learn that their team was deleted (a `TeamDeleted` input, or the
  team actor's fan-out loading the flag), so that non-members on `link`/`password` boards of a deleted team are kicked
  too. Today they stay until the board actor reloads (§10 above covers members and `team` boards).
- **U23 / UF9 (membership cache):** `MembershipCache.MembersSql` should join `teams` and filter
  `deleted_at is null` (or the rooms should learn `TeamDeleted`), so a reload after a restart or `Forget` does not
  bring a deleted team's members back to poker and board access checks.
- **U9 / UF9:** a team rename does not reach a live team room's `TeamState.Name`, and endorsement-type and template
  changes have no input either; the team snapshot shows them after the next load.
- **U25:** `TeamAccess` and `TeamActors` are there for the team-scoped board, session and comment routes.

## Verification

- `dotnet test tests/Retroscope.Integration.Tests --filter Category=TeamHttp`: 28 tests pass. They run the whole server
  as `Program.cs` composes it (`WebApplicationFactory<Program>`: real leader, actors, team room and outbox).
  Mutations checked: without the empty-roster publish the soft-delete test fails (the poker subscriber is not kicked);
  without the address comparison the email-binding test fails; letting admins remove admins fails the removal test; letting the accepting user replay an email invite fails the replay test (all three states).
