# U44 decisions: soak and chaos

U44 owns `tests/Retroscope.Soak/**`.

## What runs

`dotnet run --project tests/Retroscope.Soak -- --profile nightly --minutes 30` (the Check). Every run first runs the
oracle's self-test (planted bugs must be caught; `--self-test` runs only that, without Docker). Then it:

1. Starts `deploy/compose.test.yml` plus `tests/Retroscope.Soak/compose.soak.yml` as compose project `retroscope-soak`
   (fresh volumes), with the 1 vCPU / 1 GB cgroup limits of our slice unchanged.
2. Starts the client process `client/soak.mjs` at `nice -n 10`. It builds on `deploy/drills/client.mjs` and
   `deploy/drills/tab.mjs` (carried follow-up), creates the rooms, loads the storm boards and runs the load.
3. Turns on the client-side network faults and runs the chaos schedule for the requested minutes, checking convergence
   after every heal.
4. Stops the load, checks convergence a last time, reads the rows of every soak room from Postgres and judges the run.
   The report (`report.json`) and the client's raw results go to `artifacts/soak/<UTC time>/`. The stack is removed
   (`down -v`) unless `--keep-stack`.

`--profile short --minutes 4` is the same shape at a small size, for working on the soak.

## Load model (nightly)

| Part | Shape |
|---|---|
| Steady rooms | 20 rooms × 8 clients: 15 poker sessions, 5 retro boards (plus a second tab of each board's facilitator), 0.3 commands/s per client (Poisson) |
| Burst | Every 2 min: every client of the 20 rooms votes and locks (poker) or votes on a card (retro) within 1 s; at +2 s each poker facilitator reveals, at +3 s sends `poker.round.next` |
| Spotlight rooms | 2 poker sessions × 8: the holder moves the spotlight every 3 s and adds a round every 30 s; followers vote on the spotlight round; now and then someone tries to take it without `force` |
| Storm boards | 50 boards × 200 cards (10 guest owners, 2 tabs each), loaded before the clock starts and subscribed for the whole run |
| Network | Toxiproxy between the clients and Traefik: 150 ± 100 ms latency, 0.5 % of connections reset every 10 s, a 30 s partition between kills |
| Chaos | `docker kill -s KILL app` every 5 min; one DB restart (at 42 % of the run); one redeploy (stop and recreate) 500 ms into the burst nearest 60 % of the run |

## Gates (all must be zero)

| Gate | How |
|---|---|
| `lost_acked` | Every created round, card and comment whose command was acked (or acked `dup`) exists; edits, tickets and votes end in a state the acked commands allow |
| `duplicate` | No round, card, comment or vote row that no applied command made, and nothing a final nack refused |
| `stale_overwrite` | No two acked overwrites (`setTicket`, `card.edit`) applied on the same base version |
| `wrong_state` | Final votes (poker, including the reveal's unlocked → abstain rule; retro) match the last applied command |
| `unacked` | No command still unanswered after the final drain |
| `vote_leak` | Wire tap on every tab: no other principal's points in a snapshot, overlay or `poker.vote.state` before reveal |
| `seq_gap`, `replay_epoch` | Every tab's tx stream is gapless within an epoch |
| `reveal_twice`, `reveal_missing` | Distinct `(epoch, seq)` of `poker.round.revealed` per round ≤ 1; every revealed round outside an outage was seen |
| `timer_expired_twice`, `timer_missing` | Same for the retro timer's expiry per `endsAt` |
| `convergence` | After each heal and at the end, every tab's folded view (through the real `web/src/*/model.js`) equals a fresh snapshot for the same principal at the same `(epoch, seq)`, within 5 s |
| `rss` | The app's RSS (`/api/admin/stats` `rssBytes`, sampled every second) stays below 160 MiB, with a sample in the minute after every kill |
| `redeploy_reconnect` | Every tab is back in its room less than 15 s after the redeploy closed its socket |

Throughput (acks/s), ack latency p50/p95/p99 and the reconnect times are recorded in the report, not gated (§j).

## Decisions where the spec was silent or did not fit

1. **C# orchestrator, Node clients.** §a describes the soak as a C# console; the carried follow-up asks to reuse
   `tab.mjs`. `Retroscope.Soak` (C#) owns the stack, Toxiproxy, the chaos schedule, the RSS sampler, the database oracle
   and the verdict. `client/soak.mjs` owns the tabs and talks to it in JSON lines over stdin/stdout. The tabs fold frames
   through the browser's own models, so convergence is checked against what a real client computes.
2. **`SoakTab` extends `Tab`.** It adds what a browser tab does that the drills did not need. After a retryable nack
   (`rate_limited`, `server_busy`) it does what `room.js` does: the entry keeps its q, new commands wait behind it, and
   after a backoff the room is subscribed again, then everything unanswered is resent. The server refuses every later
   command of the room until that `sub` (U14's `RefuseRate`), so a tab that only resends is refused forever; the first
   nightly attempt stalled on exactly that while loading the storm boards. Ephemeral commands queued for more than 10 s
   are dropped (§c.8). `closed()` is overridden only to timestamp reconnects. The storm boards are filled at about
   14 commands/s per connection, under the 20/s limit.
3. **What an ack proves.** A plain `ack` proves the command was applied. A `dup` ack, or a resume `lastQ` past the q,
   proves only that the cursor passed it. A final nack lost with its socket is later answered `dup` the same way. So for
   final states the oracle accepts every outcome that a dup-acked intent allows, and the gates hold exactly for plain
   acks. Creates are never refused in this workload, so a dup-acked create must exist.
4. **Partitions** disable the Toxiproxy proxy for 30 s: every client connection is closed and new ones are refused, while
   the app and database keep running. A blackhole (Toxiproxy `timeout` toxic) would leave `client.mjs`'s
   `Socket.open` waiting on a TLS handshake whose bytes were dropped, with no timeout, which the drills' client cannot
   recover from. Half-open sockets on the server side still come from the resets.
5. **Network faults apply to clients only**, between the clients and Traefik. The app ↔ db path is exercised by the DB
   restart and the kills. Latency is on the downstream (server → client) stream, so each command's round trip carries
   150 ± 100 ms. "0.5 % resets" is read as: every 10 s, each live connection has a 0.5 % chance to be reset
   (`reset_peer` with toxicity 0.005 for 300 ms).
6. **"Within 5 s of healing".** A heal ends when the fault is lifted, the app is healthy (for outages) and every tab is
   back in its room; how long that takes is reported as `reconnectMs` (gated only for the redeploy, < 15 s, because
   `bye.retryMs` alone may be up to 8 s). The load pauses at that point, and `convergedMs` is the time from then until the
   last tab's view last changed, provided every view then equals the fresh snapshot.
7. **Restart policy.** compose.test.yml has none; production has `restart: unless-stopped` on app and db. The overlay
   adds it, because a DB restart makes the app exit (the lease watchdog, §c.9) and only the policy brings it back. After
   `docker kill` the soak also runs `compose up --wait`, in case Docker counts the kill as a manual stop.
8. **Own project, images, ports and subnets** (`retroscope-soak`, `retroscope-soak:test`, https 38443, Toxiproxy API
   38444, Mailpit 38445, subnets `172.31.144.0/24` and `198.20.144.0/24`), so the soak can run next to an e2e stack.
   Traefik's published port is removed (`!reset`); Toxiproxy publishes the https port instead, so `PUBLIC_URL` and the
   `Origin` check are unchanged. The oracle reads the database with `psql` through `docker compose exec`, not through a
   published port: on Rancher Desktop the forwarded port did not always come back after the DB restart. So the project
   needs no Npgsql and no longer references `Retroscope.Core`.
9. **Room mix.** The 20 rooms are 15 poker and 5 retro boards. Poker carries the bursts and the vote-secrecy tap; boards
   carry concurrent edits (two tabs of the author editing the same cards), votes, comments and the timer. Boards stop
   adding cards at 150 and comments at 300, as real retros do; otherwise a 30-minute run would grow every board to about
   1,500 cards.
10. **Principals.** Each room's facilitator is a signed-up user (timer and facilitation need one), the other clients are
    guests (cheaper than bcrypt signups on the 0.6-CPU app). Every principal names its own `X-Test-Client-Ip`, so the
    per-IP limits (20 sockets, signups) never bind.
11. **Toxiproxy** `ghcr.io/shopify/toxiproxy:2.12.0` pinned by its index digest (checked with `docker buildx imagetools
    inspect` on 2026-10-21). 2.13.0 was a week old, so the previous release was taken.
12. **Comparison form.** Views are compared as JSON with object members sorted, presence in pid order (the server
    sends presence sorted by pid; the board model keeps arrival order, which is not state) and a board's cards,
    comments, votes and overlay ids as sets (finding 3). `heldByThisTab` is left out because it belongs to the tab, and
    the fresh snapshot comes from a new tab of the same principal.
13. **Ordering acks.** Set-semantics outcomes (votes) are judged by the last plain ack in the order the tab received
    acks, not by seq: seq restarts with every epoch, and acks arrive in commit order on one connection.

## Findings for other units

Found by the short profile on 2026-10-21; the nightly report lists them again under its gates and warnings.

1. **Retro timer never expires after a restart (U13 `ActorTimers` / U22 `RetroRoom`; `timer_missing`).** Reproduced
   alone: start a 8 s timer on a board, `docker kill -s KILL` the app 5 s later and bring it back; the reloaded actor
   sends `retro.timer {idle, expired:true}` once, as §c.10 asks. Then start a 5 s timer (acked, `retro.timer {running}`
   sent): it is still `running` 12 s later, and a fresh snapshot agrees, so every client converges on a timer stuck at
   0:00. The soak also saw it for a timer started right after a redeploy. Every nightly run with a timer running across
   a kill should report it until it is fixed. The likely mechanism, from the code: `ActorTimers.TryTake` moves the key
   into `_fired` before the decision runs, and `TimerRules.Expire` returns `Unchanged` when `now < endsAt`. A timer
   that fires even slightly early (the delay is a `TimeSpan` of `endsAt - now`, which the BCL timer rounds to whole
   milliseconds, and a restarted process reads a different clock) leaves the timer running, and `Reconcile` then sees
   the same `(dueAt, payload)` in `_fired` and never arms it again. Fix for the U13/U22 owner: record a key as fired only
   when the decision expired it, or re-arm when `Expire` answered `Unchanged` with `now < endsAt`; regression test with a
   `FakeTimeProvider` firing before `endsAt`. The soak's `timer_missing` gate is right to fail on it, so U44 does not
   relax it.
2. **A database restart surfaces as a final `internal` nack (U13 `SqlRoomStore.CommitAsync`; reported as a warning).**
   Every `PostgresException` from the batch except `RS001` becomes `CommitRejectedException`, including the
   `57P01 admin_shutdown` / `57P03 cannot_connect_now` a restarting database sends. The actor answers `internal`
   (final), and the client drops an intent that §c.6 says must be retried: infrastructure failures should be answered
   with `bye` + 1012. Classifying SQLSTATE classes 08 and 57 as outcome unknown would fix it.
3. **Card order inside `cards` (U8 projection, U34 `retro/model.js` `toWire`).** For cards created in the same
   millisecond, the server orders by the stored microseconds and `toWire` by id, so a snapshot does not fold back to
   itself byte for byte. Nothing on screen depends on it (the board sorts cards itself); the soak compares cards,
   comments and votes as sets (decision 12).

## Check status (2026-10-21)

The nightly profile ran once for its full 30 minutes (`artifacts/soak/20261021-225046/`, not committed); the carried
instruction allows one run. 281 sockets in 72 rooms, 93,045 acked commands (about 52/s), ack latency p50 153 ms,
p95 256 ms, p99 528 ms, max 1.75 s, through 150 ± 100 ms of added latency. The convergence check after every heal passed:
four partitions, five kills, the DB restart and the redeploy, each converged within 0.2–0.6 s of the last tab getting
back. The slowest reconnect after the redeploy was 5.7 s. The wire tap saw no vote leak and no seq gap, and no command
was left unanswered. Five retro timers never expired (finding 1). There were two `internal` nacks during the DB restart
(finding 2).

That run did **not** produce a verdict. While the stack was down for a kill, a sample request ended with an
`HttpIOException`. The RSS sampler did not catch it, and it was rethrown when the run collected the sampler, before the
database oracle ran. So the RSS gate and the database gates are unknown for that run. The sampler now catches it, and a
fault in a background task no longer costs the run its verdict. A 4-minute short run after the fix (with every chaos
event) gave a verdict: every gate was zero except `timer_missing` (finding 1). Peak RSS was 74 MiB, and the slowest
reconnect after the redeploy was 2.1 s.

**The Check cannot pass until finding 1 is fixed**: any timer running across a kill or redeploy fails `timer_missing`.
