# UX13 decisions: a deploy-time track for the retro timer

The owner wanted the retro timer to play a specific recorded track. That track has no licence that permits
redistribution, and the repository will become public (tenet 6), so it can never be committed or built into an
image. UX13 lets a deployment supply its own track at deploy time and keeps the generated music (U35 decision 6)
as the default and the fallback.

UX13 adds `src/Retroscope.Server/Hosting/TimerMusic.cs`, `web/src/retro/track.js`,
`tests/Retroscope.Integration.Tests/Hosting/TimerMusicTests.cs`, `tests/web-unit/retro/track.test.js`,
`tests/e2e/fake/retro-stages/timer-track.spec.js` and this file. It edits `HostingModule` (one service and one
`Map` line), `retro/{timer,board,index}.js`, the fake server and its demo, `build.sh` (usage text only),
`deploy/docker-compose.yml` and the deploy docs.

## Decisions

1. **Deploy time, not commit time.** `MUSIC_FILE` names an absolute path inside the container. The compose file
   passes it through and has a commented, read-only bind mount of `MUSIC_DIR` at `/music`. The mount names only
   the variable, so enabling it commits no host path. The deployer holds the licence (`deploy/COOLIFY_SETUP.md`
   §5.12, `THIRD_PARTY.md`). Nothing in the repository refers to any particular track.

   `${MUSIC_DIR:?}` is required, so once the block is uncommented every Coolify resource that deploys the file
   needs `MUSIC_DIR`, the preview slot included. The docs say to point it at an existing (possibly empty) folder
   there and leave `MUSIC_FILE` empty. A default such as `${MUSIC_DIR:-…}` was rejected: Docker creates a
   missing bind source as an empty root-owned folder on the host, silently, which hides a mistyped path.

   **Superseded at the first deploy.** Coolify refuses any volume source that contains `${` (its
   `validateShellSafePath`), so the mount could not use `MUSIC_DIR`. It now names the fixed folder
   `/data/retroscope-music`. That path is already in the setup guide and identifies no track. A host without the
   folder gets an empty one, which is what the preview slot needs. The mistyped-path worry above no longer applies,
   because the only name a deployer types is the file in `MUSIC_FILE`, and a wrong one logs "does not exist".
2. **Checked once, never fatal.** At startup `TimerMusic` checks the path:
   - it is absolute;
   - its extension is in the allow-list `.mp3` (`audio/mpeg`), `.ogg` or `.oga` (`audio/ogg`), or `.m4a` (`audio/mp4`);
   - it is a regular file of 1 byte to 32 MiB;
   - it can be opened;
   - its first bytes match the type: `ID3` or an MPEG frame sync, `OggS`, or `ftyp` at offset 4.

   A failure logs `Timer music is off: <reason>` and leaves the route answering 404, and the server keeps running.
   The timer has a working fallback, so crashing would only cost uptime. The message names the problem, never
   the path. The service is resolved in `Map`, so the warning appears at startup rather than on the first request.
3. **Streamed with range support.** `GET /media/timer-music` returns ASP.NET Core's `PhysicalFile` result with
   `enableRangeProcessing`, so the bytes go from disk with `SendFile`. That result answers 206, 416, `If-Range`,
   `If-None-Match` and `If-Modified-Since`. The response carries:
   - a strong ETag built from the file's length and write time, so it can serve `If-Range`;
   - `Last-Modified`;
   - `private, max-age=86400`;
   - `nosniff` (from the global header set).

   The file is stat'd per request, so a file overwritten in place gets a new ETag without a restart. Safari
   refuses media from a server without byte ranges, and a range lets a late joiner seek without fetching the
   whole file. The route is `Guest` (any session, guests included; 401 without one) with 120 requests/min/IP
   and 60 per principal. One play makes a few range requests, so that is ample. Only a board page plays the
   track, and it already holds a session for its socket; a same-origin `<audio>` request sends the cookie. A
   deployer's licence may cover their users but not the public, so the route is not `Public` and shared caches
   may not keep a copy. Anyone can still become a guest, so this limits casual hot-linking rather than
   enforcing a licence. Only `GET` is mapped, like every other route.
4. **The boot says whether a track exists.** `TimerMusicBootContributor` adds `timerMusic: true` to the boot JSON
   of `/retro/:code` only. That is the established way a page learns server facts before it paints (no extra
   round trip), and `/api/boot` gives the same answer for in-app navigation. `retro/index.js` passes it to
   `createBoard`, which exposes it as `ctx.timerMusic`.
5. **An `<audio>` element, not an AudioBuffer.** Decoding a 4-minute stereo track into a buffer would take
   about 90 MB of PCM, on a page that already runs on phones. The element streams instead. It is made with
   `preload = 'none'`, so a board that never plays music fetches nothing. It switches to `auto` on first play
   and loops. `createMediaElementSource` routes it into the timer's AudioContext through a gain set to
   `0.3 × volume`, so the volume menu and mute work as they do for the generated music. Muting or locked audio
   stops it exactly where the generated music stops. There is one element per page, shared by every board the
   tab opens, so navigating between boards does not fetch the file again.
   The volume menu is now a slider, and the track's gain glides to a new volume (UX15).
6. **Sync.** The target is `musicPositionMs mod duration`, computed afresh on every timer tick from the server
   clock (U35 decision 4). Drift is measured the short way round the loop (`trackDrift`):
   - **Starting or resuming.** While the element is not yet playing, its `currentTime` is exact, so one look
     decides: it seeks on `loadedmetadata`, and on play when the drift is over 250 ms.
   - **While playing.** `currentTime` can lag the sound. WebKit updates it in steps and stalls it for a moment
     after each seek, and the first version, which seeked on every reading over 250 ms, seeked about twice a
     second in headless WebKit. Lag only ever makes the element look behind, so the estimate is the largest
     drift over the last 1.5 s, and at least two samples are needed. Samples are ignored for 1 s after a seek.
     Over 250 ms it seeks. From 40 to 250 ms it plays at a rate of 0.97 or 1.03, which corrects about 30 ms per
     second and cannot be heard (pitch is preserved). Under 40 ms it plays at 1.
   - **Seek spacing.** A playing element seeks at most once every 4 s and is nudged in between. That bounds the
     glitches on an engine whose playback itself keeps stalling.

   Measured against the demo with a 4 min 26 s, 128 kbps MP3:
   - Chromium and Firefox never seeked after the first alignment and stayed within 40 ms.
   - A second Chromium tab that joined 8 s in played within 25 ms of the first.
   - Headless WebKit stalls for about 300 ms every second or so. It seeked 3 times in 14 s (34 before the
     window and spacing), and between seeks it ran 0.3 to 0.9 s behind: a sawtooth with a seek on every
     4 s boundary. With the spec's silent WAV it is worse: the element stands still for about a second at a
     time, reporting that it waits for data, and falls 1 to 2.5 s behind. Turning the rate nudge off did not
     change that. See "Known gaps".
7. **Pause, stop and expiry.** The timer's `paint` decides, as it does for the generated music: anything but
   "running, music on, unmuted, unlocked, time left" calls `track.stop()`, which pauses the element and resets
   its rate. A play promise that resolves after a stop pauses again.
8. **Audio unlock (U35 decision 7).** The first pointer or key event that resumes the AudioContext also calls
   `load()` on the element. WebKit lets an element play later only if it was touched inside a user gesture,
   and with `preload = 'none'` that `load()` fetches nothing. That priming runs once, and never after the
   element has played: every board mount re-arms the gesture listeners, and `load()` on a playing element
   aborts it, empties it and fetches it again. `play()` runs only once the context is running, as the
   generated music does. A `NotAllowedError` leaves the element paused, and the next tick tries again.
9. **Fallback.** The track is abandoned for the page, and the generated arpeggio plays from the next tick, when:
   - the element fires `error` (404, a network failure, an undecodable file);
   - `play()` rejects with `NotSupportedError`;
   - `createMediaElementSource` throws.

   Without the boot flag, no element is made and nothing is fetched. `.retro-timer[data-music-source]` says
   `track` or `generated` while music plays, for the specs and for anyone checking by eye.
10. **CSP is unchanged.** `media-src 'self'` already covers a same-origin media element. The element is never put
    in the DOM, and no banned sink is used.
11. **The fake server mirrors it.** `fake.musicFile` (constructor `musicFile`) serves the file at the same path
    with single-range, `If-Range`, `If-None-Match` and 416 support, and adds `timerMusic: true` to `/retro/*`
    boots. It also accepts `.wav`, which the real server does not, because a spec can write a WAV of silence
    in a few lines and every browser decodes it. `./build.sh preview` reads `MUSIC_FILE` (or `--music-file`).
    `./build.sh preview real` passes the environment to `dotnet run`, so `MUSIC_FILE` reaches the real server
    unchanged.

## Known gaps

- **WebKit sync is unproven.** Headless WebKit never holds the 350 ms tolerance (decision 6), so the e2e spec
  records it as a known gap and asserts only its seek spacing and that playback moves. Real Safari and iOS have
  not been tried. Check them by ear before relying on the track there.
- **A corrupt file can leave WebKit silent.** The server checks only the first bytes, so an MP3 that starts with
  a frame sync but does not decode passes. Chromium and Firefox fire `error` and fall back within a second.
  Headless WebKit fired no error for a 200 KB random file with an MPEG header: it stayed on the track, silent,
  with `currentTime` jumping about. A liveness check (no steady progress for a few seconds means failed) was
  not added, because headless WebKit stalls a good file for about a second at a time and would trip it. A
  deployer should play the file once in a browser after setting it up.

## Verification

- `dotnet test --project tests/Retroscope.Integration.Tests --filter FullyQualifiedName~TimerMusicTests`: 19 of 19
  passed. The tests cover:
  - the route without a file;
  - a caller without a session (401);
  - a file overwritten in place, served from the next request with a new ETag;
  - an unreadable file (mode 000, skipped as root);
  - whole, ranged, past-the-end and revalidated requests;
  - the content types for `.ogg`, `.oga` and `.m4a`;
  - the boot flag on retro routes only;
  - a refused extension, wrong magic bytes, an empty file, a missing file, a relative path and an oversized file,
    each logging a warning without the path;
  - the per-IP limit.

  Every audio file is a few generated bytes.
- `node --test tests/web-unit/retro/track.test.js`: 16 of 16 passed. The tests use a fake element and context
  and cover:
  - the drift and correction math;
  - `preload` and `load()`, and priming only once and never after play;
  - the gain routing and its level at each volume;
  - a retry after a `NotAllowedError`;
  - the metadata seek;
  - nudging, the lagging-`currentTime` window, settling and seek spacing;
  - immediate alignment on resume;
  - no correction while seeking or buffering;
  - stopping;
  - the three fallbacks.
- `node --test tests/web-fake-server/self.test.js`: passed, including the timer-track route, ranges and boot
  flag.
- `./build.sh fake-e2e "retro-stages/timer-track.spec.js"`: 16 of 16 passed (chromium, firefox, webkit,
  mobile-webkit), twice. The spec covers:
  - two contexts playing a 20 s silent WAV (written at test time), advancing, and staying in step: over 2 s,
    90 % of samples within 350 ms of the shared position and of each other, with at most one seek each
    (WebKit: seeks only, see "Known gaps");
  - pause stopping both;
  - resume seeking both back, and staying in step again;
  - an in-app return to the board followed by a key press, which must not reload the playing element;
  - the generated fallback when the boot names a track the route cannot serve;
  - no request at all without a track.

  `retro-stages/timer.spec.js`: 24 of 24 passed.
- Self-check against the demo (`MUSIC_FILE=<a local MP3> node tests/web-fake-server/demo/main.js --port 5194`),
  driven by Playwright with the browser's real AudioContext:
  - The element reached `readyState` 4 with a duration of 265.8 s.
  - `currentTime` advanced with the timer within 40 ms.
  - Pause stopped it, and resume carried on from the paused position.
  - A forced 30 s jump was corrected within 1.5 s.
  - A late-joining second tab was in step within 25 ms.

## Follow-ups

- `docs/DESIGN.html` and `deploy/COOLIFY_SETUP.html` are stale (`docs/followups/UX13.md`).

- If a deployment wants a different level for its track, `TRACK_LEVEL` (0.3) could become a boot value.
- The browser caches the track for a day. A deployer who swaps files and wants every tab to switch at once
  would need a version token in the URL. That is not worth the complexity yet.
