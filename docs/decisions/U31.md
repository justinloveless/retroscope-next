# U31 decisions: poker table core

U31 owns `web/src/poker/{index,model,table,seats,hand,drag,reveal,keyboard}.js`, `web/styles/neotro.css` and
`tests/e2e/fake/poker-table/**`. It also created `tests/web-unit/reducers.test.js` (see decision 1).

## Contracts later units rely on

1. **`poker/model.js`** is pure. `pokerModel(me, {pending})` is the RoomStore model (U28 contract): `snapshot(d, o)`,
   `apply(state, {k, d})` and `optimistic(state, k, d)`. The state keeps the snapshot's fields flat (`rounds`,
   `observers`, `roster`, `spotlight`, `currentRoundId`, `followSpotlight`, …) plus `me`, `votes`
   (`roundId → pid → public vote`), `own` (`roundId → own vote`), `submits` (`roundId → Jira submit`),
   `presence` (sorted by pid), `heldByThisTab`, `deleted` and `nav`. `toWire(state)` gives the server's
   canonical `{d, o}` back. Intents: `voteIntent`, `lockIntent`, `abstainIntent`, `ticketIntent`. Selectors:
   `seatsOf`, `myVote`, `roundPhase`, `revealGroups`, `cardScale`, `initialRound`, `roundById`, `isObserver`.
   `uuidv7()` mints round ids.
2. **Navigation (R13).** `navTarget(prev, events, {viewed})` is the per-frame rule of `docs/decisions/U7.md`,
   checked against every transcript. The RoomStore has no per-frame hook, so `apply` records the frame's
   navigation request in `state.nav` (a new object per `poker.pointer {nav:true}` or followed spotlight
   change) and the screen calls `resolveNav(prevConfirmed, confirmed, viewed)` on each notification.
   `navTarget` is exactly `resolveNav` over one frame. When several frames land in one animation frame, the
   last request wins and a vanished target is dropped before the "my round is gone" check; the only
   difference from per-frame resolution is a target that one frame names and a later frame in the same
   animation frame deletes, which a viewer could never have seen anyway.
3. **Spotlight binding (`heldByThisTab`).** The snapshot overlay seeds it; after that the model sets it when
   a `poker.spotlight` naming me arrives while this tab's own `poker.spotlight.take` or
   `poker.spotlight.move` for that round is still in its outbox. That is exactly the tx this tab's command
   produced, because the server sends the ack after the tx frame on the same queue (§c.3), and `room.js`
   removes the entry only on the ack. `pokerModel`'s `pending()` port is `room.pending()`; `index.js` wires
   it, and `claimsSpotlight(pending, d)` is the predicate. Other `poker.spotlight` events naming me keep
   the binding when I already held the spotlight (a repair after a round delete), and leave this tab
   unbound when the spotlight just became mine without a claim (a give, another of my tabs taking it).
   Any holder other than me, or a release, clears it. U32 needs no hook: send take/move through
   `ctx.room.send` and read `view.heldByThisTab`. One case only a resync fixes: another of my tabs
   force-takes or rebinds the spotlight on the same round while this tab was bound; the event looks like a
   repair, so this tab keeps reading `true` until its next snapshot (the server would nack its moves
   `not_holder`, which U32 can treat as "unbound").
4. **Extension points for U32 and U33.** `index.js` builds the page with empty slots (`.nt-toolbar-extras`,
   `.nt-strip-slot`, `.nt-panel-left`, `.nt-panel-right`, all hidden or empty) and runs every entry of
   `FEATURES` as `feature(ctx) → {update(view, roundId), destroy()}` with
   `ctx = {room, socket, me, actions, navigate(roundId), viewed, slots: {toolbar, strip, left, right}}`.
   U32 and U33 cannot edit `index.js`; each needs one import and one `FEATURES` entry, which is a change
   request to this file's owner (or an integrator `fix(integration)` commit). `actions` holds `reveal`,
   `replay`, `end`, `nextActive`, `continueRound` and `setTicket`; `askNewRound()` in `table.js` is the
   "Start New Round" dialog the strip's "+" button can reuse.
5. **Cards.** `cardEl(frame)` / `betweenEl(low, high)` / `faceEl(points, high, abstained)` in `reveal.js` draw
   sprite frames (`data-card="5"`, `abstain`, `back`); size follows the inherited `--scale` custom property
   (71×95 at 1). U33's submit chips can reuse them.

## Decisions where the spec was silent or did not fit

1. **`tests/web-unit/reducers.test.js` has no owner in §k**, but U31's Check runs it. U31 created it with the
   poker transcripts only (plus unit tests of the poker model). U34 (same wave) will want retro transcripts in
   the same file; whoever merges second adds a retro block next to the poker one.
2. **`me` comes from `boot.me.principal.id`.** U16's boot `me` is the `/api/me` body
   (`{principal: {id, kind, name, avatar}, user, teams, …}`), not `{pid}` as U28 decision 1 words it.
   `pidOf(me)` accepts both shapes, so `welcome.me` (`{pid}`) works too.
3. **One socket per tab, created by the poker screen.** The entry stub (U29) does not open a socket, and the
   router's `mount(root, boot)` has no way to hand one over. `index.js` creates the tab's socket on first use
   (module-level, so in-app navigation keeps it) and `leave`s its room on unmount. When the principal
   changes in the tab (a guest joins, the user signs in), the old socket is stopped and a new one is created
   with the new pid. Follow-up for U29: when
   the entry opens the socket early, expose it through one shared accessor and switch `socketFor()` to it;
   two sockets in one tab would share a cid and fight over 4409.
4. **Boot snapshot.** `boot.room`, when present and naming `poker:<id>` for this code, is the viewer's
   `snap` frame (`{t:'snap', r, e, s, lastQ, d, o}`, what U13's `SnapFrameAsync` builds); the screen seeds
   the room from it. Without it the screen asks `GET /api/poker/by-code/{code}` for the id and the socket
   delivers the snapshot. Follow-up for U25: emit the member as `room`.
5. **Guests without a cookie** (`boot.me === null`) get a one-field join form that posts `/api/guest`
   `{displayName}` and uses the returned principal. Nothing else in §k covers joining a quick session as a
   new guest.
6. **End, Continue and Next Round.** On a revealed active round: when another open (active, voting,
   non-pending) round exists, "Next Round" ends this one and moves to the next open round in strip order,
   wrapping; otherwise "End" ends it and "Continue" opens "Start New Round" and sends the atomic
   `poker.round.next` (§c.4: one transaction, double-click safe) rather than `end` + `create`. The N shortcut
   does what the visible primary button does and is ignored on voting rounds.
7. **Shortcuts** use `event.code` (`Digit1`…`Digit7`, numpad too), because Shift changes `event.key`.
   Shift+N votes between the N-th card and the next one; Shift+7 does nothing. Shortcuts are ignored while a
   text field, a select, a contenteditable or an open `<dialog>` has the keyboard, and on key repeat.
8. **Seats.** Team sessions show roster ∪ present ∪ voters − observers; quick sessions present ∪ voters −
   observers (§c.4), so the quick roster (all past voters) does not seat people on every round. Order: roster
   order, then presence (pid order), then unknown voters. `presenceEnabled: false` shows everyone present.
9. **The hand's between slot is card-sized.** The original widens the merged slot to 2 cards + 15 %; here the
   merged card keeps one card's footprint in the fan, so the fan geometry does not jump. The 620 ms merge
   (two cards fly into the slot while it fades in) is played with the Web Animations API on fixed-position
   ghosts and skipped under reduced motion.
10. **Drag-to-play** uses pointer capture on the hand card, so a press that never crosses 8 px is a click
    (Shift-click included); keyboard activation (Enter/Space) arrives as a `click` with `detail === 0`.
    Escape cancels a drag. A drop sends `poker.vote.set {points, high?, lock:true}`. The 2 s hold is measured
    with `performance.now()` in requestAnimationFrame.
11. **Reveal flip.** Only a reveal that happens while the viewer looks at the round flips (300 ms delay,
    0.6 s); opening an already revealed round shows the faces. Between cards crossfade over 0.5 s. A
    replayed round clears the stacks, so its next reveal flips again.
12. **Ticket edits** are sent as typed (trimmed; empty means `null`) with the view's `version` as
    `baseVersion`; the server upper-cases and prefixes. The optimistic intent bumps `version`, so a second
    edit before the first ack is based on the version the first one will produce. The field shows upper case
    through CSS only.
13. **Visual baselines are Chromium-only** and carry Playwright's platform suffix
    (`*-chromium-darwin.png`, generated on macOS arm64). Other engines skip the visual spec; every other
    spec runs on all four projects. CI does not run fake e2e today; the first Linux run needs
    `--update-snapshots` for the `-linux` files.

## Verification

- `node --test tests/web-unit/reducers.test.js` (Node 20.19.1): 21 tests, including all five poker
  transcripts (state and `expectedNav` for every frame).
- `./build.sh fake-e2e "poker-table/*.spec.js"`: 120 passed, 24 skipped (the visual spec outside Chromium)
  on chromium, firefox, webkit and mobile-webkit. The navigation spec replays every poker transcript frame by
  frame in the browser and checks `?round=N` against `expectedNav`.
- The poker chunk is about 20 KB brotli (budget 40 KB), `neotro.css` 2.7 KB.

## Amendment (UF14)

- **Decision 3 is superseded.** The poker screen no longer creates a socket. It takes the tab's socket from the
  entry (`mount(root, boot, {socket})`) or from `getSocket()` after a guest joins (`docs/decisions/UF14.md`
  contract 1). A principal change is handled by `getSocket()`.
- **Decision 13:** the visual spec pins `timezoneId: 'UTC'` and `locale: 'en-US'`, and baselines exist for
  `-darwin` and `-linux` (UF14 decision 3).
