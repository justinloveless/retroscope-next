# U26 decisions: Jira endpoints and poker port

U26 owns `src/Retroscope.Server/Endpoints/JiraEndpoints.cs`, `src/Retroscope.Server/Jira/{BrowseService,Jql,PokerJiraPort,IslandStore}.cs`,
the `JiraHttp` JSON context (`Json/JiraHttpJsonContext.cs`, U0 decision 3) and, following the U13/U19/U21 precedent, its
tests in `tests/Retroscope.Integration.Tests/JiraHttp/**` (`Category=JiraHttp`).

## Public surface

| Type | Use |
|---|---|
| `JiraEndpoints.AddServices` | Registers `BrowseService`, `IslandStore`, `JiraAudit`, `JiraGate`, `JiraWrites` and `PokerJiraPort` as `IPokerJiraPort` (the poker room resolves the port lazily, so registration order does not matter) |
| `PokerJiraPort` | `SubmitPointsAsync` writes through the configured points field, drops the issue's cache entries and audits `jira.points`; `LoadMetaAsync` reads the 5 minute metadata cache |
| `BrowseService` | Browse (30 s per team and filters), metadata rows (5 min per issue), board sprints (5 min), session round states, `Buckets` (port of `buildJiraBrowseIssuesBySprint`) |
| `IslandStore` | The 60 s issue detail cache: fields, the description as `AdfDescription` (Doc, islands, editable), the 20 newest comments rendered, the attachment list |
| `Jql` | Escaping, `cf[NNNNN]` points filters, `statusCategory` filters, sprint scopes, `key in (…)` |
| `JiraAudit` | One `audit_log` row per Jira write (`jira.update`, `jira.transition`, `jira.points`, `jira.sprint`, `jira.comment`, `jira.link.create`, `jira.link.delete`, `jira.create`, `jira.config.set`, `jira.config.delete`); target is the issue key (link id, site host) and never content |

## Routes and shapes (for U30, U33, U36)

All under `/api/teams/{teamId}/jira`. Shapes follow `tests/web-fake-server/jira.js` and docs/decisions/U30.md; nulls are
written (`"points": null`), as the fake writes them. A missing or deleted team and a non-member get the same
`404 not_found`; a route that needs Jira on an unconfigured team gets `409 jira_not_configured`; a write the caller may
not make gets `403 forbidden`. Jira failures use §f's table: problem+json with `code`, `fields` (Jira's messages) and
`retryAfter` (seconds, also in `Retry-After`).

Browse query values: `status` = `all` (default) \| `not_done` \| `new` \| `indeterminate` \| `done` (status category
keys; the original's "Exclude Done" default is the client's `not_done`); `points` = `any` (default) \| `unpointed` \|
`pointed` \| a number; `scope` = `board` (default) \| `open` \| `all`. Anything else is `400 invalid` with the field.

## Decisions where the spec was silent or did not fit

1. **A description save always reads the issue from Jira first.** §f keeps islands in the 60 s detail cache keyed by
   `(team, key, updated)` and refetches only when the entry expired. Then an edit made in Jira within those 60 s would be
   overwritten by a save whose base is still cached, which is the lossy write F5 forbids. So `PATCH` with a description
   drops the cached detail, fetches the issue (one GET), and writes only when Jira's `updated` still equals
   `descriptionBase`, splicing that fetch's islands back. The detail entry holds the islands together with the `updated`
   they belong to, so there is no separate per-version entry. Jira has no conditional PUT, so an edit landing between
   that GET and the PUT can still be lost; the window is one round trip instead of 60 s.
2. **A description that is not an ADF `doc`** (U6: `Editable` false) has `editable:false` and `descriptionMarkup:null`,
   and a description write to it is `409 stale` (the drawer reloads, and offers no editing).
3. **`PUT …/points` does not post `JiraPointsResult`.** The poker decider ignores a result unless the round has a
   matching pending submit, so a post from the drawer would always be a no-op. The drawer's write instead drops the
   cache and calls `PokerJiraLoop.Invalidate`, like every other write. A round's recorded Jira points come only from the
   room's own submit (`poker.jira.submitPoints`), whose pending → ok/failed state every subscriber sees.
4. **Write order.** `JiraWrites.Touched` invalidates the issue's cache tag before `PokerJiraLoop.Invalidate`, so the
   rooms' refetch reads Jira and not the entry the write made stale. `PokerJiraPort.SubmitPointsAsync` invalidates
   before returning for the same reason (the loop invalidates right after a successful submit).
5. **Round states come from Postgres.** `roundState` is computed per request from `poker_rounds` of the given
   `session` (which must belong to the team): `pointing` when an active round carries the key, else `pointed`; pending
   preview rounds do not count (parity with `jiraBrowseDisabledReason.ts`). Writes are write-through, so the rows are
   current. The cached browse result is shared; the overlay is not.
6. **`includeKeys` are merged only without search text.** Keys on the session's rounds that the browse did not return
   are added (from the metadata cache) so their Pointing/Pointed reason shows. While searching they are not added: the
   search answers the text, and the original also ignored the hide filter while searching. `hidePointedOrPointing`
   likewise applies only without search text.
7. **Ranked browse.** With `scope=board`, a configured board and no search text: the board's active and future sprints
   (three at a time, ≤ 10 pages each, with the filter JQL as the Agile `jql` parameter), then issues in sprints of other
   boards in one `search/jql` (`… AND sprint is not EMPTY AND sprint not in (board sprints) ORDER BY Rank ASC`, instead of
   the original's per-orphan-sprint fetches), then the backlog. Rows are bucketed by `Buckets` (the golden-vector port),
   so sprints of other boards sort among the board's by start date and name. A failing part sets `partial:true` and
   `code` (the first error) and the rest is still shown; when nothing could be read the error is returned. Other scopes,
   search text, or no board use `search/jql` with `ORDER BY Rank ASC` (≤ 10 pages of 100). Without a board `board`
   falls back to `open`. A text that looks like an issue key (any case) is fetched by key and the filters are ignored
   (parity).
8. **JQL.** Status categories are matched by name (`"To Do"`, `"In Progress"`, `"Done"`), as the original did; the route
   takes the category keys. Epics and sub-tasks are excluded with `issuetype not in (Epic, subtaskIssueTypes())`
   (parity). A points filter without a configured points field is `400 invalid` (`fields.points = no_points_field`),
   never a guessed field name.
9. **Metadata.** Missing keys are fetched 50 at a time with `key in (…)`. Jira refuses the whole query when one key does
   not exist, so a chunk answered `jira_validation` falls back to one GET per key (four at a time; 404/403 skipped), as
   the original did. A key Jira does not know is cached as absent for the same 5 minutes. Each key has its own cache
   entry (single-flight and invalidation per key); one fetch serves every uncached key of a chunk.
10. **Settings.** `PUT` replaces `projectKey`, `boardId`, `ticketPrefix` and `pointsFieldId` (null clears; the settings
    form always sends them), keeps `membersCanEdit` when absent, and keeps the stored email or token when omitted. The
    stored email is recovered by opening the box (Atlassian emails hold no colon, so the first colon of `email:token`
    ends it). Every save probes Jira with the effective credentials (`myself`, field discovery, board resolution) before
    anything is stored; a refused token is `502 jira_auth_failed` with `fields.token` = the classic-token hint (F24).
    `pointsFieldId` given by the admin sets `points_field_overridden`; otherwise the discovered field is stored. The
    project key defaults to the resolved board's. Only a newly entered token ends `rotate_required`; a passing
    `POST /test` clears `auth_failed` but not `rotate_required`. After a save or delete: `Credentials.Invalidate`, the
    team's cache tag is dropped, and `JiraSettingsChanged` is posted to every session of the team (dropped by the
    registry for rooms that are not live, which read the row when they load).
11. **Comments** are posted with the team's Jira account, so the ADF starts with a paragraph "Sent from Retroscope by
    {display name}" (the server's name for the caller). The `201` answer has `author: null` (Jira's author is that
    account) and the body as sent.
12. **Create.** `fromRetro: true` parses the description as retro markup (8,000 code points, `MarkupField.ActionItem`),
    so a "Create in Jira" from an action item turns mentions into `@Name` and board images into their alt text
    (U6 decision 10); otherwise the Jira dialect (32,000). The project is `projectKey`, else the clone source's, else the
    configured project key or ticket prefix. A clone copies the source's type, project and every description block
    byte for byte, and appends a "Cloned from KEY" paragraph. Creating drops the team's cached browse results.
13. **Links.** `direction: outward` (default) makes this issue the link's outward side (parity with
    `manage-jira-issue-link`). Jira's create answers without an id, so the answer is read back from the issue's links
    (the newest of that type to the target), or built from the request when Jira does not list it yet. `DELETE
    links/{id}` names no issue, so every cached drawer of the team is dropped.
14. **Attachments** must appear in the issue's `attachment` field (from the detail cache); anything else is
    `404 jira_not_found` without calling Jira. The bytes are sent with `Cache-Control: private, max-age=300`,
    `Content-Security-Policy: sandbox` and `nosniff`; U19's client enforces the raster types and the 5 MiB cap.
15. **Caches** all live in U19's one 8 MB `JiraCache`. Every entry carries the team tag; browse entries also the browse
    tag and each row's issue tag; detail entries the issue tag and a team "details" tag. Options: edit meta per issue and
    link types per team for 1 h, transitions per (issue, status) for 60 s, assignable users per (issue, query) for 60 s.
16. **Rate limits:** `jira.read` 600/min per principal and 1,200/min per IP; `jira.write` 120/240; `jira.settings`
    30/60; `jira.attachment` 300/600.
17. **The port resolves the Jira client on first use.** The poker room builds `PokerJiraLoop`, and with it the port,
    when the host starts; the client needs `APP_KEYS` (U19 decision 17), which hosts without Jira traffic (the route
    inventory and leader process tests, tools) do not set. `PokerJiraPort` therefore takes `Func<JiraClient>` and
    `Func<BrowseService>`, like `PokerJiraLoop` takes `Func<ActorRegistry>`.

## Follow-ups for other units

- **U33:** the shapes and query values above. `editable` gates description editing; `descriptionMarkup` is the editable
  description as markup with island refs, so the drawer need not serialize the Doc itself; send `updated` as
  `descriptionBase`. Browse takes `session` and `hidePointedOrPointing` and answers `roundState` per row.
- **U36:** "Create in Jira" posts `{summary, description: <card text>, fromRetro: true}` to `POST …/jira/issues`.
- **U48 (web fake server):** `jira.js` should accept `status=not_done|all`, `points=any|<number>`, `session`,
  `hidePointedOrPointing`, `fromRetro`, and answer `editable`/`descriptionMarkup`, so the screens see what the server
  sends.
- **U19 / FakeJira:** the fake ignores JQL (sprint, backlog and search pages return every issue), so filter-to-JQL is
  tested on the request bodies, not on results.

## Verification

- `dotnet test tests/Retroscope.Integration.Tests --filter Category=JiraHttp`: 32 tests pass. They run the real hosting,
  database, leader, actor, transport, poker room, membership cache, Jira client and these endpoints on Kestrel loopback
  against a migrated Testcontainers database and FakeJira, with fake time: ranked bucket order (start date, natural
  name, backlog last, sprints of other boards), Pointing/Pointed (pending rounds excluded, session keys merged), the
  hide filter ignored while searching, filters as JQL on `cf[10016]`, the key fast path, partial results, the 30 s
  shared cache (a second member costs 0 Jira calls; a write drops it), metadata caching and limits, one metadata fetch
  for 10 WebSocket clients and the title refresh after a `PATCH`, a submit pending for everyone then ok (decimal 2.5
  stored) or failed with `jira_validation`, `jira_pending` on a second submit, decimal points over HTTP, byte-for-byte
  island splice-back, `stale` after a concurrent Jira edit and for an unknown island, read-only non-ADF descriptions,
  write-only credentials, the token required for a host change, the rotate-required banner, the classic-token hint,
  the connection test, settings reaching live poker rooms, `members_can_edit`, audit rows, attachment id validation,
  create, clone and create from a retro action item, error mapping; plus the golden sprint-bucket vectors and JQL
  escaping.
- Mutation checks: applying the hide filter while searching fails the Pointing/Pointed test; skipping the cache
  invalidation in `JiraWrites` fails four tests (the room title refresh, the shared-cache drop, the island save and
  the members-can-edit save).
