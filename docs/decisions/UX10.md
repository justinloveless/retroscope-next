# UX10 decisions: the rich Jira description editor, server path

The owner asked to "recreate the full rich text editor experience" for Jira descriptions, without Atlassian's editor
library. A design review compared a ProseMirror prototype with a native one and recommended ProseMirror, with the server
as the only authority on what reaches Jira. This file records the owner's decisions and the server path as built
(delivery phases 2a, 2b, 2c and 3). The client phases (4 onwards) add their own sections.

UX10 so far changes `src/Retroscope.Core/Adf` (`AdfSchema`, `AdfEditProjection`, `AdfWrite`, `AdfTableGrid`),
`src/Retroscope.Server/Endpoints/JiraEndpoints*.cs`, `Jira/IslandStore.cs`, `Jira/JiraClient.cs`,
`Json/JiraHttpJsonContext.cs`, FakeJira, the web fake's Jira, their tests and fixtures, `THIRD_PARTY.md`,
`tools/quick.mjs` and DESIGN §f.

## Owner decisions (2026-10-23)

1. **Approvals 1 to 5 of the design review are accepted:**
   1. ProseMirror is the first runtime web dependency, pinned to exact versions, with a pin test so an extra package
      fails CI.
   2. `prosemirror-view`'s `readHTML` is rewritten at build time, pinned by the file's sha256, so no `innerHTML`
      assignment ships.
   3. A budget of about 90 KiB brotli for a lazily loaded `rich-editor` chunk (final number set from the production
      build).
   4. Projected ADF reaches the browser, only for users with `JiraEditIssues` and only when they open the editor. This
      revises UX8 decision 1 ("raw ADF never reaches the browser") for editors; viewers keep the Doc.
   5. Whole-document saves through `descriptionAdf` on the issue PATCH replace the markup-with-islands description
      path (DESIGN §f F5) once the web client has moved over.
2. **Prefetch.** The editor chunk is prefetched when the issue drawer opens for a user who can edit.
3. **Mention search and image upload are in scope** (phases 9 and 11). The validator has hooks for both now
   (decision 13).
4. **The emoji picker is out for now.** Existing emoji nodes are kept and edited as atoms.
5. **Real-Jira gates G1 to G3 passed** on 2026-10-23. The owner ran them by hand against a throwaway issue on a Jira
   Cloud site, with a classic API token, and deleted the issue afterwards. Nothing in this unit called real Jira.
   - **G1, uploaded media renders.** The upload answered 200. `GET attachment/content/{id}` without `redirect=false`
     answered 303 to `api.media.atlassian.com`, and its `Location` held the media uuid. With `redirect=false` the
     same request answered 200 with the bytes and no `Location`, so the upload path (phase 11) must read the id from
     the default, redirecting request. A `media{type:file, id:<uuid>, collection:""}` node written through REST v3
     was kept with that id and rendered in Jira's own UI.
   - **G2, the full node set.** A description holding `layoutSection`, `nestedExpand` in a table cell,
     `decisionList`, `status`, `date`, `embedCard` and a pixel-width `mediaSingle` answered 204, and a read-back
     10 s later held every node type, with `widthType: "pixel"` kept. The first attempt was overwritten 74 ms after
     the write by a project automation that sets a description template on create. Jira had accepted it, as the
     issue history showed. Edits made right after an issue is created can race such automations.
   - **G3, user search.** `user/viewissue/search` answered 200 with results.

## Server design as built

6. **One allow-list, pinned to Atlassian's schema.** `Core/Adf/AdfSchema` is the single table of nodes, marks,
   attributes (type, enum, range, length and value rule) and content contexts. The projection and the validator both
   read it.
   - The contexts mirror `full.json`'s groups (`doc`, `block_content`, `table_cell_content`, `nestedExpand_content`
     and the per-node content of panel, blockquote, listItem, lists, tables, layouts, media and so on), including
     which block marks a paragraph or heading may carry in each.
   - Preserve-only nodes (`extension`, `bodiedExtension`, `inlineExtension`, `syncBlock`, `bodiedSyncBlock`,
     `placeholder`, `mediaInline`, `blockTaskItem`) are in the table, so a token's placement can be checked, but are
     never editable.
   - `@atlaskit/adf-schema` 57.7.2 `dist/json-schema/v1/full.json` is vendored under `tests/fixtures/adf-schema/57.7.2`
     with its Apache-2.0 licence (recorded in `THIRD_PARTY.md`). 57.7.2 was published on 2026-10-07, so it meets the
     two-week rule. The tarball's integrity hash was checked against the registry.
   - `AdfSchemaTests` requires that every schema node is in the table and nothing else is; every schema mark is edited
     or explicitly preserved; node attributes are exactly the schema's; mark attributes are the schema's minus the
     media-link ones; every enum, range and content expression is within the schema's. A schema bump fails these
     tests with the difference listed.
7. **The projection** (`AdfEditProjection.Project`) is pure and stores nothing.
   - A node passes through when its type is editable, allowed in its context, within depth 28 and node 5,000, has only
     known members, and its required and structural attributes are valid.
   - Otherwise it becomes `{"type":"rsOpaque","attrs":{"ref":R}}`, or `rsOpaqueInline` in inline content. `R` is
     `AdfLossiness.IslandId` of the node.
   - An unknown mark, an invalid one, a second mark of a type, or a mark not allowed in the combination (code with
     anything but link) becomes `{"type":"rsMark","attrs":{"ref":R}}`.
   - Unknown attributes and invalid optional values move into one `rsKeep` attribute whose ref hashes the stashed
     members.
   - The edit view also carries a media table (each media id and the attachment the proxy serves for it, through
     `AdfMediaMap`), the distinct opaque parts with a label and a read-only Doc preview, the distinct mark tokens, and
     the caps the save is held to.
8. **The validator** (`AdfWrite.TryWrite`) rebuilds the save with `Utf8JsonWriter` from the allow-list and never
   echoes the client. It parses with duplicate keys, comments and trailing commas refused, and a depth bound derived
   from the depth cap.
   - **Tokens.** Each `rsOpaque`, `rsMark` and `rsKeep` is replaced by the original bytes from Jira's current copy,
     the i-th use of a ref getting the i-th original, so repeated parts come back byte for byte too.
   - **Values.** New hrefs and card urls must be in normalised form (`AdfHref.Allowed(x) == x`) with no format, space
     or private-use characters; an href Jira already wrote into the description may stay as it is. Colours are strict
     `#rrggbb`; a status hex colour only if the description already has it.
   - **Structure.** Content contexts with their min and max counts; `mediaSingle` holds media then an optional
     caption; tables must be rectangular with spans counted (`table_shape`), unless the base had the same ragged table
     by `localId` (each such `localId` excuses one table of the save); `colwidth` gives one width per spanned column; task and decision `localId`s are unique; a panel colour
     only on a custom panel; a `mediaSingle` width over 100 needs `widthType: "pixel"`, which needs a width.
   - **Media.** A file or link media node must be one the description holds; its `type`, `id`, `collection`, `alt`,
     `occurrenceKey` and `url` are copied from Jira's copy, and only `width`, `height` and `localId` come from the
     client. External media may only stay where Jira had them.
   - **Mentions.** An id must be one the description already mentions or one `KnownAccount` returns; a known account's
     text is rewritten to `@` and its display name. Members a hook writes are never written again from a stash.
   - **Tokens' limits.** A token may appear at most as often as the base holds it (`opaque_duplicated`), and only where
     its original type may stand or where the base had it (`opaque_misplaced`). A mark token counts as a mark of its
     kind: the same ref twice on one node, or a token beside a client mark of its kind, is `invalid_mark`, unless Jira's
     copy itself had that mark beside another of its kind. `rs*` names anywhere else are `reserved_name`. A ref the base does not hold is reported as missing, which the endpoint answers as `stale`.
   - **Caps** are the larger of the default and the base: nodes 5,000, depth 28, text 32,000 code points, bytes 1 MiB.
     Nodes and bytes are enforced while writing, before each original is copied in, because a token or stash of a few
     dozen bytes can stand for a much larger original: the validator stops at the cap instead of building the whole
     document first.
   - **Read-back depth.** An original copied in may not make the description nest deeper than 62 JSON levels (the doc
     object counting 1): Jira's issue JSON holds the description two levels down and the server reads issues at the
     default 64, so a deeper save could never be read back (`too_deep`).
   - **Errors.** At most 20, each a code and a dotted index path such as `content.3.content.0.attrs.href`, never
     content. A member name the allow-list does not know is shown as `?`, so a path only ever names allow-listed
     members and indices.
9. **Error codes:** `invalid_json`, `not_doc`, `conflict`, `too_large`, `too_deep`, `too_many_nodes`, `too_long`,
   `unknown_node`, `invalid_nesting`, `invalid_attr`, `invalid_mark`, `invalid_text`, `invalid_href`, `invalid_color`,
   `table_shape`, `duplicate_local_id`, `unknown_media`, `invalid_media`, `unknown_mention`, `opaque_duplicated`,
   `opaque_misplaced`, `reserved_name`.
10. **Invariants, pinned by FsCheck** (`AdfWritePropertyTests`, over a generator of descriptions that mixes valid
    content with what Jira also sends: preserve-only and unknown nodes, unknown marks and attributes, refused values,
    ragged tables and repeated task ids):
    - saving the unedited projection writes back a document equal to Jira's, with every opaque part and mark byte for
      byte; the same holds for every description fixture;
    - random edits an editor may make (rewrite text, add bold, drop, swap or add a top-level block) validate and keep
      every remaining opaque part's bytes.
11. **`GET /api/teams/{teamId}/jira/issues/{key}/description`** (`JiraEditIssues`, route policy `TeamMember`, rate
    limit `jira.read`, `Cache-Control: no-store`). It reads the issue from Jira rather than the 60 s cache, so the
    editor starts from Jira's copy:

    ```jsonc
    {
      "key": "RS-12",
      "updated": "…",        // the save's descriptionBase
      "editable": true,      // false (and adf null) when Jira's description is not an ADF document
      "adf": { "type": "doc", "version": 1, "content": [ … ] },
      "media": [ { "id": "<media id>", "attachmentId": "10001", "name": "shot.png", "image": true, "w": 640, "h": 360 } ],
      "opaque": [ { "ref": "<16 chars>", "kind": "extension", "inline": false, "label": "…", "preview": { /* Doc */ } } ],
      "marks": [ { "ref": "<16 chars>", "kind": "annotation" } ],
      "limits": { "nodes": 5000, "depth": 28, "text": 32000, "bytes": 1048576 }
    }
    ```
12. **`PATCH issues/{key}` gains `descriptionAdf`**, exclusive with `description` (`fields.descriptionAdf =
    "conflict"`); either needs `descriptionBase` (`required`). `null` clears the description to an empty document.
    - Before any Jira call: the body is at most 1 MiB (route metadata, 413 `too_large`), and `descriptionAdf` must be an
      object of type `doc` (`not_doc`).
    - Then the issue is read again from Jira. A moved `updated`, a description that is not a document, or a token the
      current copy does not hold answers 409 `stale` with `current.updated`.
    - Any other refusal is 400 `invalid` with `fields.descriptionAdf` = the first code and `fields["descriptionAdf.at"]`
      = its path.
    - Then the PUT, the audit row and the fresh issue view, as for every issue write.
13. **Hooks for later phases.** `AdfWriteContext.Upload(mediaId)` (phase 11's upload ledger) and
    `AdfWriteContext.KnownAccount(accountId)` (phase 9's known-account set) default to "none". With them unset, a
    save can only keep the description's own media and mentions. The hooks are synchronous lookups. The fallbacks
    server-path §2.5 and §5.2 describe for after a restart (checking up to 10 unknown mention ids through user search,
    resolving up to 10 unknown media ids from the issue's newest attachments) need Jira calls, so phases 9 and 11
    extend `TryWrite` to also report the mention and media ids it could not resolve (ids only, never content); the
    endpoint resolves them asynchronously and validates once more.
14. **Fakes.**
    - FakeJira can serve a description as raw text (`RawDescriptions`), so tests compare the bytes Jira sent with the
      bytes it receives, and it refuses a description that carries a server token name, so it is never more lenient
      than Jira about our own tokens.
    - The web fake's Jira serves `GET issues/:key/description` and accepts `descriptionAdf` with the server's
      precondition, `conflict`, `required` and `not_doc` refusals. It validates no content, and it answers any save
      that carries a token `stale`, because its edit views never hold one.
      RS-12 and DEMO-123 now carry ADF. `WebFakeAdfTests` checks that it renders, through `AdfToDoc`, to exactly the
      Doc the fake serves from markup and islands, and that it projects to itself, so the fake serves it unchanged.
      Other issues get ADF built from their markup. After a rich save the fake's read view is rebuilt from the ADF:
      markup kinds keep their shape and other blocks become plain-text islands (enough for phase 6 to start; extend it
      if a spec needs more).
15. **Nothing new is stored.** The projection, refs and caps are computed per request from the issue Jira returns; no
    ADF, filename or account id reaches Postgres or a log line. A test asserts that no captured log line carries
    description text.

## Deviations from the design review

- **Invalid optional values are stashed, not opaque.** The review made any node that fails a value check opaque. Here
  only required and structural attributes (cell spans and widths) do; an invalid optional value (a code language with
  a space, a `var(--ds-…)` cell background) goes into the node's `rsKeep`, so one odd attribute does not lock a block.
  A stashed value comes back only when the client does not set that attribute.
- **Marks have no stash.** A mark with an unknown attribute, such as a media link's `id`, `collection` or
  `occurrenceKey`, is an `rsMark` as a whole.
- **Structural parents go opaque.** A child that would be a token inside a list, table, row, layout section, media
  single or group, decision list or code block makes its parent the token instead, because ProseMirror's content
  expressions for those nodes cannot hold an atom of another type. Task lists keep token children (they may hold
  `blockTaskItem`).
- **Placement is also kept where Jira had it.** A token may stand where its type may stand or in any context it had in
  the base, so a node Jira wrote in a place the schema does not allow survives a no-op save.
- **Mention `accessLevel` comes from the client** (a string of at most 32 characters) rather than being copied from the
  base: two mentions of one account may carry different values, and copying the first broke the no-op invariant.
- **Not enforced:** the first-child rule of `listItem` (`full.json` has none) and the sum of layout column widths (its
  tolerance is unverified). `status.style` is limited to `bold` and `subtle`; other values are stashed.
- **Comment and new-issue modes are not built.** The review's `AdfWriteMode` will come with the phase that moves
  comments and creates to ADF.
- **Escaping.** The validator writes with relaxed JSON escaping (only what JSON requires), so text costs the same bytes
  as in Jira's copy and a large non-ASCII description does not grow past its cap on a no-op save.
- **Raw invalid UTF-8 in a string is `invalid_text`,** not `invalid_json`: `Utf8JsonReader` does not validate string
  contents at parse time, and the string read refuses it.
- **`JiraClient.UpdateIssueAsync` writes the description's own bytes** (`WriteRawValue`) instead of re-serialising the
  element, so opaque parts reach Jira exactly as Jira wrote them. The markup path is unaffected in meaning.
- **The edit depth cap is 28, not `AdfToDoc.MaxDepth` (32).** ASP.NET binds request bodies at the default 64 JSON
  levels. In a PATCH body a node at ADF depth k sits at level 2k + 2, and a link mark's attributes on a text node three
  levels further down. At 28, even a token one level past the cap, or a client text node at the view's `limits.depth`
  with a link, binds, so the client always gets the coded `too_deep` instead of a body the binder drops. Deeper nodes
  are tokens. An earlier commit parsed projected and rebuilt descriptions at 256 levels instead; with the cap and the
  read-back bound it is no longer needed and was reverted.
- **DEMO-123's coloured bold text** (`demoColours`) was `fg{b{…}}` in the fake's island and is now `b{fg{…}}`, the
  nesting the server's reader produces. It looks the same.

## Open items

- **Deep descriptions.** Jira issues are read at the default JSON depth of 64, so a description nested deeper than
  about 30 ADF levels cannot be read at all, by the drawer or the editor. This predates UX10; raising the limit needs a
  decision.
- **Opaque content in the web fake (prerequisite of phase 6).** The fake's edit views never hold a token, so the
  phase 6 and 7 specs cannot yet exercise locked atoms, `rsMark` text, `rsKeep` or a save that carries tokens. Before
  those specs: give a fake issue an extension, an inline extension, an annotation mark and an unknown attribute; have a
  Core test (like `WebFakeAdfTests`) write its projected edit view (`adf` with tokens, `opaque` with previews, `marks`)
  and the originals as a committed golden the fake serves; and have the fake restore tokens from it on save instead
  of answering `stale`. It is not done here because it changes a fixture issue's read view, and with it the fake e2e
  specs and visual baselines that phase 6 re-baselines anyway.
- **The client's schema must match the allow-list (before phase 5).** Phase 5 builds the ProseMirror schema, which must
  mirror `AdfSchema` exactly: per-context `OpaqueChildren`, paragraph and heading block marks per context,
  `TextMarks` and `CodeTextMarks`, attribute rules, an `rsKeep` attribute on every node and the token names. The plan
  follows `ProtocolCatalogTests` and `protocol.gen.js`: a Core test serialises `AdfSchema` to a committed generated
  module under `web/src` (regenerated by running the test, checked by CI's clean-tree step), and phase 5's web-unit
  test builds the ProseMirror schema from it or asserts equivalence against it.
- **`docs/DESIGN.html` is stale**: DESIGN §f changed (the description routes and "Rich description editing") and the
  HTML copy was not regenerated.
- **Phase 12** deletes the markup description path (`DescriptionMarkup`, `IslandIds`, island splicing for
  descriptions) once the web editor uses `descriptionAdf`.
