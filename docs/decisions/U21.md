# U21 decisions: poker room

U21 owns `src/Retroscope.Server/Realtime/Rooms/PokerRoom.cs`, `src/Retroscope.Server/Realtime/Stores/PokerStore.cs`,
the `PokerRoom` JSON context (still the U0 placeholder: the room needs no JSON types of its own) and, following the U13
and UF4 precedent, its tests in `tests/Retroscope.Integration.Tests/PokerRoom/**` (`Category=PokerRoom`).

## Public surface (for U22, U23, U25, U26, U27 and the integrator)

| Type | Use |
|---|---|
| `PokerRoom.AddServices` | Registers the store, the binding (`services.AddRoom`), the Jira loop and the room gateway |
| `PokerBinding` | The runtime binding: `FromClient` via the implicit `PokerInput` conversion, `DurabilityOf` → `evt.Durability`, `Supersedes` → all `SpotlightMoved`, `WarmUntil`, `IsDeleted`, `OnShutdown` → `SpotlightSettleDue` while the spotlight is dirty, `CanSubscribe` → `Policy.Can(Subscribe)` |
| `PokerRoomDomain` | `PokerDomain` plus the room's effects outside the actor (Jira submit, meta loop, team tallies) |
| `PokerStore` | `SqlRoomStore` subclass: one-batch load, SQL per committed event |
| `PokerJiraLoop` | The `JiraMetaLoop` and off-actor submits. `Invalidate(team, key)` is how the Jira proxy (U26) refreshes a key after a PATCH, transition or points write (R15b) |
| `RoomGateway` | `IRoomGateway` for every room kind (see decision 1) |
| `IResumeFill` | Unsequenced frames a room kind hands a subscriber right after its `snap`/`replay` |

## Decisions where the spec was silent or did not fit

1. **The gateway lives here.** U14 left `IRoomGateway` for U13, U13 shipped `IRoomPeer` and the registry but no
   gateway, and the carried follow-up gives "rooms implement `IRoomGateway`" to U21–U23. One gateway serves every
   room kind, so `RoomGateway` is generic: it adapts each `(connection, room)` to an `IRoomPeer`, calls the
   `ActorRegistry` without blocking the receive loop, and is registered with `services.Replace` (the transport's
   `TryAdd` ran first). It sits in `PokerRoom.cs` only because that is the file U21 owns; **U22 and U23 should reuse
   it, not add their own**, and the integrator may move it under `Realtime/Actors/` (UF7's folder). Details:
   * An actor's kick is a serialized frame, so the peer recognises `{"t":"kick"` and calls
     `IClientConnection.Kick`, which makes the connection forget the room (otherwise a kicked room would keep its
     slot under the 10-room cap and the connection would keep forwarding commands).
   * A room kind with no registered `RoomType` (retro and team until U22/U23) is kicked `not_found` instead of
     reaching the registry, which would throw.
   * A new subscription refused `Busy`, or one that could not be handed over, restarts the connection (1012); there
     is no nack for `sub`, and the client resumes after `bye.retryMs`.
2. **`jira.meta` reaches clients as `x` frames only.** `PokerSnapshot` has no `jiraMeta` field (Core is not U21's), so
   the loop keeps titles per room and every subscriber gets the cached `x jira.meta` frames right after its `snap` or
   `replay` (`IResumeFill`). Fills and broadcasts go only to peers that already received their snapshot, so a
   subscriber that is about to be kicked `forbidden` never sees a title.
3. **The loop's trigger is `Timers`.** The runtime asks for timers after every message it handled, on the actor's
   thread, so `PokerRoomDomain.Timers` is where the room notices new ticket keys, whatever produced them (load,
   create, setTicket, clearAll). Each key is requested once per room; new keys are fetched together after 250 ms
   (`PokerJiraLoop.Coalesce`) in one `LoadMetaAsync` call, the result is broadcast, and `JiraMetaLoaded` is posted to
   the actor, which persists only parent keys that changed. A failed fetch is logged and not retried until the key
   is invalidated (metadata is never needed for correctness). Only team sessions with Jira configured fetch. A room's
   cache is dropped once its actor state is gone and nothing is in flight.
4. **No `JiraMetaInvalidated` input.** Core's `PokerInput` has none, and an invalidation needs no decision:
   `PokerJiraLoop.Invalidate(team, key)` re-fetches the key for every live room of the team that requested it. A
   successful submit invalidates its key too.
5. **Submits.** Applying `JiraSubmitChanged{pending}` starts `IPokerJiraPort.SubmitPointsAsync` off-actor with a 10 s
   timeout (the injected `TimeProvider`); the result is posted back as `JiraPointsResult`. An exception or timeout is
   `failed` with `jira_unavailable`; with no port registered, `failed` with `jira_not_configured`. A result for a room
   that was evicted meanwhile is dropped (pending lived only in memory, §c.10).
6. **`sort_key` is the round's index in `Order`.** `RoundCreated` shifts the keys at and after its `SortKey` up,
   `RoundDeleted` shifts the keys after the deleted round down, `RoundsReordered` rewrites all of them with
   `unnest … with ordinality`, `RoundsReset` writes 0. The deferred unique constraint absorbs the transient
   duplicates. This relies on dense keys in the database, which every plan preserves and the importer writes (`PokerMap.MapRounds` numbers each session's rounds from 0).
7. **`last_activity_at` is coalesced in SQL**: every committed plan ends with
   `update … set last_activity_at = now() where id = $1 and last_activity_at < now() - interval '1 minute'`, an
   index lookup that writes nothing within the minute. No per-room memory is needed.
8. **Reveal SQL** is the spec's `update poker_votes set abstained, locked, points = null, high_points = null where
   round_id = $1 and not locked` plus the round row; replay rewrites the round's votes from the event (it drops
   observers' votes, decision U7-9).
9. **Load.** A session of a soft-deleted team loads as missing (`not_found`, §c.11). Jira counts as configured when
   the team has a `team_jira_config` row; its `status` is the proxy's business, and U26 posts `JiraSettingsChanged`
   when the settings change. Only string values of `teams.point_descriptions` are read. `WarmUntil` = load + 15 s.
   The roster is the team's members (team sessions) or the principals with a vote (quick sessions, R27).
10. **Session delete** removes the `poker_sessions` row (rounds, votes and observers cascade) and the room's
    `client_cursors`. HTTP (U25) asks the actor with `DeleteSession` and the caller as viewer.
11. **Team tallies.** For team sessions, `ITeamNotices.PokerChanged(team, session, pointed, total)` fires when
    *pointed* (revealed committed rounds) or *total* (committed rounds; pending previews are not counted) changes.
    The first sight of a room after a load does not notify. U25's session-list SQL should count the same way.
12. **Optional collaborators.** `IPokerJiraPort` (U26) and `ITeamNotices` (U23) are resolved with `GetService`, so the
    room works before they exist. `IAccessView` is required by `AddRoom`, so `PokerRoom.AddServices` adds a deny-all
    `NoTeamAccess` with `TryAdd` (quick sessions work, team sessions refuse everyone); **U23 must register the real
    view with `AddSingleton` or `Replace`, not `TryAdd`**, so its registration wins.

## Follow-ups for other units

- **U22/U23:** reuse `RoomGateway` (decision 1); register rooms with `services.AddRoom`. Give a room kind's cache fills
  through `IResumeFill` if it needs any.
- **U23:** register `IAccessView` so it replaces `NoTeamAccess` (decision 12); post `RosterChanged`,
  `PointDescriptionsChanged` and `AccessChanged` to live poker rooms (`ActorRegistry.Post` / `AccessChanged`).
- **U25:** delete a session with `ActorRegistry.AskAsync<PokerState, PokerInput>(room, new DeleteSession(), viewer)`;
  the boot snapshot is `QueryAsync(room, view => view.SnapFrameAsync(viewer))` as U13 says.
- **U26:** register `IPokerJiraPort`; call `PokerJiraLoop.Invalidate(team, key)` after every write through the proxy;
  post `JiraSettingsChanged` to the team's live poker rooms when the Jira config changes; `PUT issues/{key}/points`
  posts `JiraPointsResult` as §f says.

## Verification

- `dotnet test tests/Retroscope.Integration.Tests --filter Category=PokerRoom`: 23 tests pass (run repeatedly, three times on the final code). They
  start the real hosting, database, leader, actor, transport and poker modules on Kestrel loopback against a
  migrated Testcontainers database, with fake time. Every poker command goes over a real WebSocket and is followed by
  the Plan/Load round trip (the actor's state and a fresh load describe the same session); plus reveal SQL, reorder
  under the deferred constraint, delete and clearAll with the spotlight held, spotlight settle and shutdown
  persistence, auto-reveal once across five clients and only after warm-up, a restart mid-round with resumed clients,
  vote secrecy on live frames, snapshots and replays, the meta loop and submits through a fake `IPokerJiraPort`,
  kicks, presence, deletion and the team tallies.
- Mutation checks, each caught by at least one test: reorder SQL disabled, reveal SQL not abstaining, vote values
  projected to everyone, no settle on shutdown, warm-up run at load, kicks passed through as raw frames, no fills
  after a snapshot, no Jira submit.
- `./build.sh test` passed. One earlier full run failed
  `PostgresFixtureTests.More_databases_than_postgres_has_connection_slots_can_be_created` (U1's fixture test, which
  counts backends on its own fresh databases and saw one more than zero); it passed in isolation twice and in the
  next full run, and U21 code never touches those databases.
