# UX19 decisions: Microsoft Entra sign-in removed

The owner judged Microsoft Entra ID sign-in too much scope for its value. Supporting it safely needed a tenant
allow-list, a per-tenant map of trusted email domains, the `xms_edov` optional claim (whose wire form U18 could not
verify), a second issuer rule and its own fake, all for one sign-in button. Google, email and password, and the emailed
sign-in link cover the same people. The owner decided to remove Entra entirely.

This narrows DESIGN §0.1 (a new "Microsoft sign-in" row) and §e (Google is the only OIDC provider). It drops no core
feature. Google sign-in, password sign-in, the magic link, password reset and verification are unchanged.

## Decisions

1. **One OIDC provider.** `OidcProvider` and the route shape `/auth/oidc/{provider}/start` and
   `/auth/oidc/{provider}/callback` stay, with Google as the only provider. An `entra` path answers 404 `not_found`,
   as any unknown provider does. `/api/me/identities/{provider}/link` keeps its shape; linking Entra is refused the
   same way. Boot JSON `oidc` lists at most `["google"]`.
2. **Entra-only code is deleted.** The Entra authority and endpoints, the tenant allow-list, the tenant domain map, the
   `xms_edov` trust rule, the `tid` issuer check and the `tid:oid` subject go, with `ENTRA_CLIENT_ID`,
   `ENTRA_CLIENT_SECRET`, `ENTRA_TENANT`, `ENTRA_ALLOWED_TENANTS`, `ENTRA_TENANT_DOMAINS` and the test-only
   `ENTRA_AUTHORITY_URL`. Code that only existed to choose between two providers is simplified where it became
   trivially dead; the Google path is not refactored.
3. **`AuthMethod.Entra` and `OwnershipProof.Entra` are removed.** The re-auth rule for adding a first password (U16,
   S17) now accepts a Google or magic-link session younger than 10 minutes.
4. **The front end shows Google only.** The sign-in card, the welcome page, `/invite` and the account page lose the
   Microsoft button, the "Link Microsoft" button and the `entra` session label.
5. **The audit log keeps its history.** `audit_log` rows written for Entra sign-ins, links and claims stay as they are.

## Data: migration 0004

`db/migrations/0004_remove_entra.sql`, applied by the migrator at start-up:

- Delete the `sessions` rows with `auth_method = 'entra'`. Those users are signed out.
- Delete the `external_identities` rows with `provider = 'entra'`.
- Narrow `external_identities_provider_check` to `('google')` and `sessions_auth_method_check` to
  `('password','google','magic_link')`.

Accounts stay. A user whose only sign-in was Entra keeps their account, teams and history, and signs in with an
emailed sign-in link or a password reset to the same email. A user who had also linked Google keeps that link.

`tests/schema.snapshot.sql` is regenerated (`RS_UPDATE_SCHEMA_SNAPSHOT=1`); its diff is the two narrowed checks.

## Deploy

The release contracts in one step, like UX18, but it stays rollback-safe. The previous binary still runs on the 0004
schema: it reads nothing that 0004 removed, and its migrator ignores an applied migration it does not know. Only an
Entra sign-in on it would fail, at the narrowed checks. `deploy/RUNBOOK.md` §11 has the steps.

- Before the deploy, delete the `ENTRA_*` variables from the Coolify resource. The new binary ignores them, but a
  rollback pins the previous commit's compose file, which still passes them on. The previous binary disables Entra
  while `ENTRA_ALLOWED_TENANTS` is empty, so with the variables gone a rollback past UX19 shows no Microsoft button.
- The owner may delete the Azure app registration once the deploy is healthy.
- `deploy/COOLIFY_SETUP.md` section 7 (Entra setup) is reduced to a note. The later sections keep their numbers, so
  every reference to them stays valid.

## Not done

- No message tells a signed-out Entra user why their session ended or how to get back in. The sign-in screen offers
  the emailed sign-in link, which is the way back.
- Older decision records (U16, U18, U29, U43, U45, UP1, UX18) and `docs/followups/after-wave4.md` still describe Entra
  as it was. U18 carries an amendment that points here; the others are left as records. The `tenant_not_allowed`
  sign-in error code that U29 and the follow-up list no longer exists: the server never sends it and the sign-in
  screen no longer has a line for it.
