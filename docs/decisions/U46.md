# U46 decisions: import rehearsal against production

U46 owns `deploy/IMPORT_RUNBOOK.md`. The carried follow-up for this wave lets it extend `expected-columns.json`,
`html-textonly.json` and the mappings, with tests, where real data shows they are wrong. The rehearsal ran against a
`pg_dump` of production restored into a throwaway `postgres:15`, and every container, volume and key it used was
removed afterwards. No row content is recorded here.

## Production findings folded into the repository

`plan` against production first failed on three schema differences. The HTML histogram had nothing unknown (only `p`,
`br`, `a` and `em`), so `html-textonly.json` and the mappings are unchanged.

1. **Eleven `auth.users` columns are `varchar(255)`, not `text`.** These are `aud`, `role`, `email`,
   `encrypted_password`, `email_change`, and the six token columns. GoTrue creates them that way. `phone` and
   `phone_change` stay `text`. `expected-columns.json` now says `varchar`, and the fake source
   (`Infrastructure/Supabase/00-platform-stubs.sql`) declares the same types, so the U38 note "unverified against a live
   project" is now verified. The snapshot already reads `varchar` through its `::text` fallback.
2. **Sixteen GoTrue tables were unlisted.** They are `custom_oauth_providers`, `mfa_recovery_code_sets`,
   `mfa_recovery_codes`, `oauth_authorizations`, `oauth_client_states`, `oauth_clients`, `oauth_consents`,
   `saml_providers`, `saml_relay_states`, `schema_migrations`, `scim_tokens`, `scim_users`, `sso_domains`,
   `sso_providers`, `webauthn_challenges` and `webauthn_credentials`. Each one is now an `exclude` entry (counted, never
   read), as the UF4 amendment to U38 decision 5 prescribes. The fake source gets a one-column stub of each, because an
   `exclude` table that is missing fails preflight like any other.
3. **`public.team_action_item_comments` does not exist in production.** Its migration (`20250822130500`) was never
   applied there, and `types.ts` also omits it (U38's note). It is removed from `expected-columns.json`, and the fake
   source skips that migration (`ImporterDatabases.NotInProduction`). If the table ever appears, preflight fails with
   "unknown table". The operator then allow-lists it (`allowArchiveOnly`) and it is archived whole, which is what §h.2
   intended for it. A test covers both outcomes, and the runbook says so. I chose removal over a new "optional table"
   flag. A missing expected table should keep failing: an absent table that the importer expects usually means the
   wrong database.

The existing test that adds an unlisted `auth` table used `auth.webauthn_credentials`, which the fake now has. It uses
an invented name instead.

## Smaller fixes found by running the verbs

4. **`IMPORT_STORAGE_URL` must be the project origin.** The importer appends `storage/v1/object/public/<bucket>/<name>`
   to it. A bucket URL, the form the dashboard shows and the one the follow-up named, would double the path and fetch
   nothing. `ImporterSettings` now refuses any value that has a path, a query or a fragment, and names the expected
   shape in the error.
5. **The source connection disables GSS encryption by default**, unless the value names a GSS setting itself.
   Npgsql's default probe loads `libgssapi_krb5`, which the importer image lacks, and printed an error for every
   connection. Supabase offers no GSSAPI. This is the same reason U43 decision 3 gives for the app.

## Runbook decisions

6. **Ship the whole database, not `--data-only`.** §h.1 says `pg_dump -Fc --data-only`, but the VPS database already
   holds `schema_migrations` and `system_state` rows once the app has started, so a data-only restore would collide on
   them. The runbook restores a full `pg_dump -Fc` into a recreated database instead, with
   `pg_restore --exit-on-error --no-owner --no-acl`. That is `deploy/RUNBOOK.md` section 8's backup restore, which is
   already tested. The app's migration checksum guard then proves that the import target was migrated by the same
   release. The roles are not in the dump. The app recreates `retroscope_app` and its grants on start.
7. **The import target is migrated by the release's app image** (`spot-load --sample 1` on the empty database). The
   importer creates no schema, and the leader runs the migrator when it takes the lease. There is no separate migrate
   verb, and adding one would mean editing the frozen `Program.cs`.
8. **The dump path needs platform stubs.** A dump of `public` and `auth` has no Supabase roles (RLS policies name
   them), no `extensions` schema (column defaults call `extensions.uuid_generate_v4()`), and no `storage` or `cron`.
   The runbook creates the roles and extensions, and reuses the `storage` and `cron` part of the test stubs. A
   `pg_dump` 17 archive needs a 17 client, so `pg_restore` runs from `postgres:17` against the `postgres:15` server.
   Image digests were checked on Docker Hub on 2026-10-21: `postgres:15` index
   `sha256:c99dd506…c174` and `postgres:17` index `sha256:a63c1ea3…1939`.
9. **Rehearsal storage listing.** The dump has no `storage.objects`, so the rehearsal listed each profile's own
   `avatars/<user id>.<ext>` object from its `avatar_url`, in the throwaway source only. At cutover the importer reads
   the live project's listing, where other buckets' objects become `manifest_only`. `cron.job` was empty for the same
   reason.
10. **`IMPORT_ADMIN_EMAILS` was empty in the rehearsal.** Admin rights belong to the operator, so no address was
    guessed. The one source `role='admin'` account was ignored and listed, as designed. The runbook tells the operator
    to set the variable to at least their own account.
