# U29 decisions: shell screens and the entry

U29 owns `web/src/entry.js`, `web/src/screens/**` and `tests/e2e/fake/shell/**`.

## Contracts later units rely on

1. **`screens/app.js` is the tab's shared state.** Room screens (U30, U31, U34) import from it instead of
   creating their own connection:
   - `getSocket()` returns the tab's one socket (U28's `createSocket`), created on first use with
     `pid = me.principal.id`; `start()` is idempotent, so a screen calls `getSocket().start()` and then
     `socket.room(key, model)`. The socket's default `onNack` toasts unhandled final nacks.
   - `session` is a store of `{me}`, where `me` is the `/api/me` body (`{principal:{id, kind, name, avatar},
     user?, teams, unreadMentions}`, U16) or `null`. `currentMe()`, `currentUser()`, `setMe()`,
     `refreshMe()` and `signedIn(me)` read and write it. U28's note says `pid = boot.me?.pid`; the real
     shape is `boot.me?.principal?.id`, and `getSocket()` uses that.
   - `navigate(to, {replace})` is the router's in-app navigation; `safeReturn(value)` validates `?return=`
     paths; `avatarUrl(principal)` is `/blob/{id}`; `signOut({everywhere})`.
   - A quick-room screen whose visitor has no principal yet creates a guest first (`POST /api/guest`),
     calls `setMe(...)`, and only then `getSocket().start()`.
2. **The entry** adopts the boot JSON (sets `me`, applies the theme) on the first page and on every
   `/api/boot` load, starts `createRouter()` from `core/router.js`, and starts the socket at once on room
   paths (`/poker/:code`, `/teams/:tid/poker/:code`, `/retro/:code` and `/teams/:id`)
   when `me` is set, so the WebSocket handshake overlaps the route chunk download (§g.1). Signed-out
   visitors get no early socket: `/ws` needs a principal.
3. **The "Reconnecting…" notice** (§g.4, offline > 10 s) and the terminal 4401/4403 notice are shown by
   `app.js` for whichever screen holds the socket, so room screens need not draw them.
4. **`screens/frame.js`** is the shell's page frame (header with navigation, unread-mentions badge, theme
   menu and account menu; a centred main column) plus form helpers (`field`, `form`, `errorText`). Room
   screens draw their own chrome and do not use it.

## Decisions where the spec was silent or did not fit

1. **No shell stylesheet.** The shell has no stylesheet of its own: `web/styles/**` and `ROUTE_STYLES` in
   `build.mjs` belong to U10, and nobody owns a `shell.css`. Shell screens use the kit classes for every
   component and set their few layout rules (grids, rows, widths) through `h()`'s style objects, which
   go through the CSSOM and satisfy the CSP (§e). Follow-up for U10: a `shell.css` in `ROUTE_STYLES` for
   `screens/*.js` would let these move into a stylesheet.
2. **Link tokens.** `/auth/magic`, `/auth/reset`, `/auth/verify` and `/invite` read `#t=` and remove the
   fragment from the address bar at once (`history.replaceState`). When a visitor must sign in first
   (verify, invite), the token waits in `sessionStorage` (`rs.verify`, `rs.invite`) and the return path is
   the bare page, so the token never appears in a query string the server would log. The specs assert
   that no request path or query carries it.
3. **Magic link.** §e names a "preview POST" for the masked address without a route; the client uses
   `POST /api/auth/magic/preview {token} → {email}` (masked), then `POST /api/auth/magic/consume {token}`
   only on the click, and accepts either the `/api/me` body or an empty response (it then reloads
   `/api/me`). U17 should map these routes or ask U29 to align.
4. **Verify.** Signed out, the page never posts `verify/consume`; it shows "Sign in to finish verifying".
   Signed in, it posts; a 401 or 403 (another account's session) shows the same sign-in prompt.
5. **Sign-up** answers 202 without a session (U16 decision 6), so the client signs in with the same
   credentials right after. If that login fails (the address already had an account), it says to check
   the inbox and stays put, which reveals nothing the server did not.
6. **Shapes not yet fixed by their server units**, read from §d and kept tolerant (arrays or
   `{items}`; missing fields render as empty):
   - `GET /api/dashboard` → `{teams, favorites, boards:[{code, title, teamName, lastAt}],
     sessions:[{code, teamId, teamName, lastAt}]}` (U24).
   - `GET /api/teams` → `[{id, name, description, role, favorite}]`; `POST /api/teams` → `{id}` (U24).
   - `POST /api/invites/accept` → `{teamId}`; error codes `email_mismatch`, `email_unverified`,
     `expired`, `revoked` (U24).
   - `GET /api/me/mentions` → `{items:[{sourceKind, boardCode, boardTitle, author|null, body (markup),
     createdAt, names?}], next}` (U25). Bodies are rendered with U5's `parse`/`render`.
   - `GET /api/me/endorsements` → `[{emoji, typeName, fromName, teamName}]` (U24).
   - `POST /api/me/identities/{provider}/link` → `{url}` for the browser to follow (U18): a fetch cannot
     follow a cross-site 302, and the CSRF header rules out a plain form post.
   - `PUT /api/me/avatar` takes the raw image bytes (U20); the client crops to 128 px WebP, or PNG where
     the browser cannot encode WebP.
   - Admin: `GET /api/admin/users?q=` → `[{id, name, email (masked), isAdmin, disabled}]`,
     `GET /api/admin/teams?q=` → `[{id, name, memberCount}]`, `GET /api/admin/stats` → a flat object
     shown as a key/value list (U27).
   - OIDC failures return to `/login?error=<code>` (`account_exists`, `tenant_not_allowed`,
     `provider_disabled`; anything else gets a generic line) (U18).
7. **Member pages while signed out** (`/dashboard`, `/teams`, `/account`, `/mentions`, `/admin/*`)
   navigate to `/login?return=<path>` instead of rendering a sign-in form in place.
8. **Admin sections** are `/admin/users`, `/admin/teams` and `/admin/stats`; `/admin` goes to users.
   Membership repair takes a user id and a role, because §d has no admin route that lists a team's
   members.
9. **Theme on in-app navigation.** Every adopted boot JSON re-applies its `theme` exactly as the pre-paint
   script resolves it (boot preference, else the stored one, else system), so the screen after a sign-in
   takes the account's theme without a reload.
10. **The account theme control is a row of buttons, not `ui/select.js`.** WebKit (desktop and mobile)
    reports a `style-src-attr` CSP violation whenever a native `<select>` is attached to the page,
    whatever its attributes; the fixtures fail any test with a violation. U10 owns `select.js`; any
    screen that renders it will fail the WebKit projects.

## Test notes

- **First paint.** The no-flash spec answers the entry module with an empty script, so the screenshot shows
  only what the shell HTML, the stylesheets and the inline pre-paint script produce; a later load runs
  the app and the theme must not change. Holding the entry back instead does not work: Firefox and
  WebKit never finish a screenshot while a module script is pending.
- **Playwright's WebKit screenshots inject an inline `<style>`**, which the page's CSP reports as a
  `style-src-elem` violation (with `caret: 'initial'` too). `theme.spec.js` drops exactly those reports in
  tests that took a screenshot, after a short wait because the reports arrive asynchronously. U48 may
  want this in the harness for visual-baseline specs (U31, U34).
- Shell routes are smoke-tested in both themes. The room routes belong to U30, U31 and U34; the shell
  specs only check that they open the socket early.
