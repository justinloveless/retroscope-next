# U18 decisions: OIDC (Google and Microsoft Entra)

U18 owns `Server/Auth/Oidc.cs`, `Server/Endpoints/OidcEndpoints.cs`, `Server/Json/OidcJsonContext.cs` (transferred
per U0 decision 3), `tests/Fakes/FakeOidc/**` and its tests in `tests/Retroscope.Integration.Tests/Oidc/**`.

## Contracts later units rely on

| Type / route | Use |
|---|---|
| `GET /auth/oidc/{google\|entra}/start?return=` | 302 to the provider; sets `__Host-rs_oidc`. Unknown or disabled provider: 404 `not_found` |
| `GET /auth/oidc/{provider}/callback` | 302 to the flow's `return` on success; on failure 302 to `/login?error=<code>` (sign-in) or `/account?error=<code>` (link flow) |
| `POST /api/me/identities/{provider}/link` | Body optional: `{return?}` (unknown members refused). 200 `{url}`; the front end navigates to `url`. Default return `/account` |
| Boot JSON `oidc` | Array of the enabled providers (`["google","entra"]`), so the sign-in screen shows only working buttons (U29/U30 front end) |
| `OidcOptions` | Registered with `TryAdd`; tests (and U45's fake stack) may register their own, e.g. with `CreateHandler` routing to the fake |
| `Retroscope.Fakes.FakeOidc.FakeOidcServer` | Google at `/google/{authorize,token}`, Entra at `/entra/{tenant}/oauth2/v2.0/{authorize,token}`, pictures at `/picture/…`; `Claims` is the next user |

Callback error codes: `oidc_state`, `oidc_denied`, `oidc_failed` (token endpoint), `oidc_issuer`, `oidc_audience`,
`oidc_expired`, `oidc_nonce`, `oidc_subject`, `oidc_tenant`, `email_required`, `account_exists`, `account_disabled`,
`oidc_conflict`, `link_session`, `identity_linked_elsewhere`.

## Spec citations (§k: "PR cites …"; there is no PR in this repo, so they are recorded here)

**OpenID Connect Core 1.0 §3.1.3.7, item 6** (fetched 2026-10-21 from openid.net/specs/openid-connect-core-1_0.html):
"If the ID Token is received via direct communication between the Client and the Token Endpoint (which it is in this
flow), the TLS server validation MAY be used to validate the issuer in place of checking the token signature. The
Client MUST validate the signature of all other ID Tokens". The server only ever reads ID tokens from its own
token-endpoint response over TLS (`Oidc.ExchangeAsync`), never from the browser, so the signature is not checked.
Items 3–5 (aud contains our client id; `azp`, when present, must be us), 9 (`exp`), 10 (`iat` may reject tokens issued
too far from now) and 11 (`nonce` must be present and match) are implemented in `IdTokenValidator`.

**`xms_edov`** (fetched 2026-10-21 from learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference,
page dated 2026-07-22): "Boolean value indicating whether the user's email domain owner has been verified. An email is
considered to be domain verified if it belongs to the tenant where the user account resides and the tenant admin has
done verification of the domain. Also, the email must be from a Microsoft account (MSA), a Google account, or used for
authentication using the one-time passcode (OTP) flow. Facebook and SAML/WS-Fed accounts do not have verified domains.
For this claim to be returned in the token, the presence of the `email` claim is required." The same page says of
`email`: "This value isn't guaranteed to be correct, and is mutable over time". This confirms §e's reading: trust the
Entra email only with `xms_edov` true or a domain listed for that tenant. **Still unverified:** the wire form. The page
says "Boolean" without an example, so `true`, `"true"`, `"1"` and `1` are all read as true; anything else as false.
Entra apps must request `xms_edov` (and `email`) as optional ID-token claims; the RUNBOOK owner (U43) should say so.

## Decisions where the spec was silent or did not fit

1. **Configuration.** `GOOGLE_CLIENT_ID`/`_SECRET`, `ENTRA_CLIENT_ID`/`_SECRET`, `ENTRA_TENANT` (default
   `organizations`), `ENTRA_ALLOWED_TENANTS` (comma list, case-insensitive), `ENTRA_TENANT_DOMAINS`
   (`tid=d1|d2,…`). A provider is enabled when its id and secret are both set; only one of them is a startup error on
   first use. Entra is disabled while the allow-list is empty (S5), even when its client is configured. Endpoints are
   static (Google's from its discovery document, checked 2026-10-21: `accounts.google.com/o/oauth2/v2/auth`,
   `oauth2.googleapis.com/token`; Entra `login.microsoftonline.com/{ENTRA_TENANT}/oauth2/v2.0/{authorize,token}`).
   Three optional overrides exist for the fake-provider stack: `GOOGLE_AUTHORIZE_URL`, `GOOGLE_TOKEN_URL`,
   `ENTRA_AUTHORITY_URL`. Issuer checks never use them: Google `https://accounts.google.com` or
   `accounts.google.com`, Entra exactly `https://login.microsoftonline.com/{tid}/v2.0`.
2. **The flow cookie** `__Host-rs_oidc` holds `{provider, state, nonce, verifier, return, linkUser, expiresAt}` sealed
   with `Keyring` (`KeyPurpose.OidcCookie`, AAD `oidc-flow:v1`), so state and nonce never appear in clear. It is
   `HttpOnly; Secure; SameSite=Lax; Path=/`, 10 minutes, and the expiry inside the box is checked too. The callback
   deletes it whatever it holds. **Single use is also enforced server-side:** a matching state is remembered until the
   flow expires, so a captured cookie replayed with its callback URL is refused (`oidc_state`). The set is in memory
   (one process, §c.9) and does **not** survive a restart: after one, a replayed cookie is accepted again until it
   expires (at most 10 minutes). What backs it then is the provider: the authorization code is single-use and bound to
   the PKCE verifier, so a replayed callback fails at the token endpoint (`oidc_failed`). Expired states are swept on
   each callback; the set holds at most the flows started in the last 10 minutes. One cookie per browser: starting a
   second flow in another tab replaces the first.
3. **`return`** goes through `Core/Security/ReturnPath` (U3) at start, then travels sealed. An unusable value is
   replaced by `/dashboard` (`/account` for linking) rather than failing the sign-in; "reject" in §e is read as "never
   redirect there". The corpus test covers `//`, `/\`, `/%09/`, single and double percent-encoded slashes and
   backslashes, absolute URLs (same origin included: only paths are accepted), CR/LF, tabs, spaces and `javascript:`.
4. **Token checks.** `exp` and `iat` both allow ±5 minutes (§e says "±5 min"; applying it to `exp` too tolerates the
   same clock skew). `aud` may be a string or an array; with more than one audience, or whenever `azp` is present,
   `azp` must equal our client id (OIDC Core items 4–5). Subjects longer than 200 characters (the column limit) are
   refused. The Entra subject is `lower(tid):lower(oid)`.
5. **Linking order** follows §e literally: linked subject → sign in (even if the provider email changed); trusted email
   → link to a verified account, or claim an unverified one (`AccountClaims.ClaimAsync`, then link, then sign in), or
   create a verified account; untrusted email → never by email: `account_exists` if the address is taken, else create
   an **unverified** account. A token without a usable email cannot create an account (`email_required`: `users.email`
   is not null). Disabled accounts get `account_disabled`. Concurrent sign-ins that race on the email or subject retry
   the resolution (three attempts), so the unique constraints decide and nothing is half-created: the user, the
   identity and the audit row are one transaction.
   **A claim unlinks the squatter's identities.** Before `ClaimAsync`, every `external_identities` row of the still
   unverified account is deleted (one transaction, conditional on `email_verified_at is null`, one `auth.unlink` audit
   row `{provider, reason: "claim"}` each). Those identities came from an untrusted-email sign-in that created the
   account, or from the squatter's own explicit link; left in place they would sign in to the verified account. The
   owner's identity is linked only after the claim. Two limits, recorded for the follow-up below: the delete and the
   claim are separate transactions (`AccountClaims` is U16's), so an explicit link completed by a still-signed-in
   squatter in the instant between them survives; and a magic-link claim (U17) does not unlink at all.
6. **Explicit link flow.** The callback requires that the browser is still signed in as the user who started it
   (`link_session` otherwise), refuses a subject linked to anyone else (`identity_linked_elsewhere`) and accepts one
   already linked to the same user. Linking does not sign in again, verify the account or require an email match: the
   user is already authenticated, and the identity's email is irrelevant to an explicit link. Unverified users may
   link (the route is `RoutePolicy.User`); a later claim removes those links (item 5).
7. **Profile picture.** Fetched only when an identity is newly linked or an account created, only when the user has no
   avatar, only from `https://lh3.googleusercontent.com` (exact host, default port, no user info), with redirects off,
   a 10 s timeout and the 256 KiB avatar cap; then `SniffedImage.TryCreate` and `BlobsRepo.InsertAvatarAsync`.
   After any new link (sign-in or explicit) `Sessions.EvictUser` drops the user's cached principals so live sessions
   pick up the avatar. The
   `users.avatar_blob_id` update is conditional on the avatar still being empty, and the blob is deleted in the same
   statement if another write won. A failed fetch or a non-image never fails the sign-in. Entra pictures need Graph
   and are not fetched.
8. **Names.** A new account's `full_name` is the `name` claim when it is plain text of at most 100 characters, else
   empty (the display name falls back to "Player"). `preferred_username` is never stored: it is often an address and
   display names must never be emails.
9. **Audit.** `auth.signup` (new account) and `auth.link` with `{provider, email_trusted}`, `auth.claim` from
   `AccountClaims`, `auth.unlink` `{provider, reason}` when a claim drops a squatter's identity, and `auth.login` with `{method, ip}` (the audit prefix) as password login writes it.
10. **Rate limits.** start and callback 30/min/IP; link 30/min/IP and 10/min/principal.
11. **Test location.** §k lists no test folder for U18; the tests sit in `tests/Retroscope.Integration.Tests/Oidc/**`
    as U16 and U20 placed theirs. `OidcHost` registers Hosting, Db, Auth, Me, Guest, Blob and OIDC modules on a
    `TestServer` and routes the picture host to the fake with a `DelegatingHandler`.

## Verification

- `dotnet test tests/Retroscope.Integration.Tests --filter Category=Oidc`: 78 tests pass.
- Mutations, each reverted afterwards: dropping the server-side consumed-state check, the untrusted-email refusal, the
  Entra issuer check or the `azp` rule each turns at least one test red (10 failures in total). Dropping the
  pre-claim unlink fails both squatter-identity tests; dropping the sign-in `EvictUser` fails the eviction test.
- `dotnet publish src/Retroscope.Server -c Release -r osx-arm64` (Native AOT): no trim or AOT warnings. The only
  warnings were two clang module-cache messages from the local toolchain, unrelated to the code. The AOT binary was not
  exercised against the OIDC routes; `./build.sh aot-smoke` was not run.
- `./build.sh test`: green (2,727 .NET tests, 243 web unit tests, golden vectors).

## Follow-ups for other units

- **U16/U17 or the integrator (`AccountClaims`):** move the unlink into the claim itself (`UsersRepo.Claim`'s
  transaction: `delete from external_identities where user_id = $1` plus `auth.unlink` audit rows), so it is atomic
  with the verification and also covers the magic-link claim. `OidcAccounts.UnlinkBeforeClaimAsync` can then go.

- **U29/U30 (front end):** read `boot.oidc` for the buttons; start sign-in with a plain navigation to
  `/auth/oidc/{p}/start?return=<path>`; link from Account settings with `POST /api/me/identities/{p}/link` then
  `location.assign(url)`; map the `?error=` codes above to messages (`account_exists` is §e's "An account with this
  email exists. Sign in with your existing method, then link Microsoft from Account settings.").
- **U43 (deploy, RUNBOOK):** document the Entra app registration (redirect URI `PUBLIC_URL/auth/oidc/entra/callback`,
  optional ID-token claims `email` and `xms_edov`) and the Google one (`/auth/oidc/google/callback`).
- **U45 (compose.test.yml):** `FakeOidcServer` is in-process only; a container for the e2e stack needs a small
  entry point and the three endpoint overrides above. Pictures on `lh3.googleusercontent.com` will not resolve there,
  which the server tolerates.
