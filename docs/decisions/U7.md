# U7 decisions: poker domain

U7 owns `src/Retroscope.Core/Poker/**`, `tests/Retroscope.Core.Tests/Poker/**` and `tests/golden/transcripts/poker-*.json`.

## Public surface (for U13, U15, U21, U25, U26, U31, U40, U48)

| Type | Use |
|---|---|
| `PokerDomain : IRoomDomain<PokerState, PokerInput, PokerEvent>` | What the actor runs. `new PokerDomain()` checks permissions with `Policy.Can`; tests pass a `PolicyCheck` |
| `PokerState`, `Round`, `Vote`, `Spotlight` | Mutable state, built by the store's `Load` (U21). `WarmUntil` = load time + `PokerTiming.WarmUp` |
| `PokerInput` | `ClientCommand(PokerCommand)` (implicit conversion from any `PokerCommand`) or an internal transition: `AutoRevealDue`, `SpotlightGraceDue`, `SpotlightSettleDue`, `JiraPointsResult`, `JiraMetaLoaded`, `RosterChanged`, `PointDescriptionsChanged`, `JiraSettingsChanged`, `DeleteSession` |
| `PokerEvent` + `Durability` | `Committed` events need SQL in the command's transaction; `Ephemeral` ones are applied, sequenced and projected but never written; `MemoryOnly` ones are applied only (no SQL, no wire event). A decision with no `Committed` event needs no transaction or cursor write |
| `PokerProjection.Snapshot/Overlay/Events` | The shared public document, the per-viewer overlay and the tx events for one viewer |
| `PokerReactions.Timers` | Every timer that should be armed now, by key; a key that is not returned should be cancelled |
| `Scoring.Winner`, `Deck`, `AutoReveal`, `TicketKeys` | Pure helpers; the importer (U40) can recompute winners with `Scoring` |

## Decisions where the spec was silent or did not fit

1. **Internal transitions are not `PokerCommand`s.** U2 decision 3 says internal commands may derive from `PokerCommand`,
   but U2's `Every_concrete_payload_type_has_exactly_one_kind` test scans the whole Core assembly and fails for any
   concrete `Command` without a catalog kind. So the domain's command type is `PokerInput`: a client command converts
   implicitly to `ClientCommand`, and internal transitions derive from `PokerInput`. U13's `RoomActor` wraps the parsed
   `Command` with that conversion. (Follow-up for U2: either keep this pattern for retro and team, or narrow the test.)
2. **Permissions go through an injectable `PolicyCheck`.** `Policy.Can` is U9's deny-all stub until U9 merges, and the
   matrix is U9's to test. Production uses `Policy.Can`. The tests use `TestPolicy`, which encodes the poker rows of
   §c.11: team sessions need a member who is a user; deleting rounds, clearing and deleting the session need admin or
   owner; Jira submits need Jira configured and `members_can_edit` or admin. Quick sessions: anyone with the code;
   deleting rounds and clearing need a signed-in user; only the creator deletes the session. Facts passed:
   `Room`, `Team`, `CreatedBy`, `IsObserver`, `JiraConfigured`, `MembersCanEditJira`. Capabilities: vote, lock and
   abstain → `PokerVote`; reveal and replay → `PokerRevealOrReplay`; create, createMany, next, end, activate,
   setTicket, commit/discard pending and reorder → `PokerManageRounds`; delete → `PokerDeleteRound`; clearAll →
   `PokerClearAllRounds`; settings → `PokerUpdateSettings`; observer → `PokerSetObserver`; spotlight commands →
   `PokerSpotlight`; Jira → `PokerSubmitJiraPoints`; session delete → `PokerDeleteSession`. U9 must allow these.
3. **Nack order and codes.** Vote-type commands check, in order: `observer`, `forbidden`, `not_found`,
   `round_pending`, `round_revealed`, `round_inactive`, then the command's own rule (`invalid` for off-deck points or a
   wrong between end, a no-op for an identical resend, `vote_locked`). Other choices:
   * Set semantics give a NoOp instead of a nack: reveal of a revealed round, replay of a voting round, end of an
     inactive round, activate of an active one, commit of a committed round, release with no holder.
   * `round_not_voting`: activating a revealed round (replay it instead). `round_revealed`: setTicket on a revealed round.
   * `not_holder`: spotlight move from a tab that is not the bound tab, release or give by a non-holder, a pending create
     without holding the spotlight, and commit or discard of someone else's pending round.
   * `invalid`: a taken round id, a bad ticket key, a batch of 0 or more than 50, deleting the last round, discarding a
     committed round, giving the spotlight to someone who is not present, Jira points that are not a multiple of 0.5
     in 0–1000, a submit for an unrevealed round or one without a ticket.
   * `not_found`: an unknown round, an observer target the session has never seen, and every command after the
     session was deleted.
   * `jira_not_configured` comes before the permission check, so a quick session gets it rather than `forbidden`.
4. **`stale` payloads (`d.current`).** next → `{roundId}` (the current pointer); reorder → `{order}`; setTicket →
   `{ticketKey, version}`; settings → `{presenceEnabled, followSpotlight}`. `spotlight_held` carries `{holder}`.
   A setTicket whose normalized key equals the current one is a NoOp even with an old `baseVersion`.
5. **Spotlight follows only its holder.** `next` says the spotlight follows only if the holder issued it. The same rule
   applies to non-pending create, createMany and (implicitly) commit: when the holder's own tab issues them, the
   spotlight moves to the new pointer round. A pending create always moves the spotlight to the preview.
6. **Spotlight and pointer repair.** Removing a round first moves a spotlight on it to the pointer round, or, when the
   pointer round is the one going, to the repaired pointer target: the highest-numbered remaining committed round
   (else the highest-numbered round). The pointer moves there with `cause:'repair', nav:false`. With no rounds left,
   the spotlight is released and the pointer is null. Delete does not change which rounds are active.
7. **next ordering.** The new round, the pointer and the holder's spotlight move come first, then pending rounds are
   discarded (their spotlight repair lands on the new round), then the other rounds are deactivated. The client
   applies the frame atomically, so only the set of events matters.
8. **Fill placeholder.** It needs a ticket key, and the current round must be voting, committed, ticketless and
   without votes. A pending create can fill it (parity). A createMany that filled the placeholder still moves the
   pointer to its last round with `nav:true`. A create that only filled the placeholder leaves its round id unused, so
   a redelivery of it would create a round; the persisted cursor (§c.8) prevents that, as for every command.
9. **Replay drops observers' votes** (emitted as `poker.vote.state` with `status:'empty'`), so no voting round ever
   holds an observer's vote. Replay also emits `poker.round.updated` with the whole round, so clients need no rule of
   their own for version, winner, `revealedAt` or `autoReveal`.
10. **Auto-reveal arming.** Every vote change, observer change, presence-enabled change, roster change, join and leave
    bumps `AutoRevealGen` and sets `ArmedAt` through the memory-only `AutoRevealArmed` event. `Timers` asks for
    `AutoRevealDue(round, gen)` at `ArmedAt + 600 ms` only while the round is ready and the room is warm. The due
    transition re-checks generation, warm-up, the 600 ms and readiness. The spec's "at least one vote is not abstained
    or everyone abstained" always holds once every eligible principal is locked, so it has no code.
11. **Holder absence.** A `Left` of the holder records `HolderAbsentSince` (memory-only `HolderAbsence`), and `Timers`
    asks for `SpotlightGraceDue` 3 minutes later. A `ClientGone` of the bound tab unbinds the tab with a committed
    `SpotlightChanged` (which persists `spotlight_client_id = null`). The 10 s client and principal graces are the
    presence table's (U13); the domain reacts to the `ClientGone` and `Left` deltas.
12. **Spotlight settle.** A move sets `Dirty`. `Timers` asks for `SpotlightSettleDue` 500 ms after the last move, and
    any decision that has a committed event appends `SpotlightSettled` (persists round and bound tab), so the next
    command's transaction carries the position (§c.8).
13. **Quick-session roster.** Team sessions get their roster from `RosterChanged`. A quick session seats a principal
    (from the caller's `Principal`) on their first vote or abstain, with a `poker.roster` event. The store loads it as
    the principals with votes, which is the R27 trim. Nothing removes a seat while the actor lives.
14. **Jira.** `submitPoints` emits an ephemeral `pending` (U21 or U26 calls `IPokerJiraPort` when it sees it). A
    `JiraPointsResult` that does not match the pending entry is a NoOp. Success on a round that still carries the key
    persists `jira_points*` (`JiraPointsRecorded`, projected as `poker.jira.points{ok}` plus the updated round);
    success after the ticket changed only clears the pending entry. Failure keeps `failed` with its code until the next
    submit. Pending and failed entries are in the snapshot's `jiraSubmits`. `JiraMetaLoaded` persists parent keys that
    changed and pass the key pattern, without a version bump (a parent refill must not invalidate a ticket edit).
    Titles stay with U21/U26. `JiraSettingsChanged` (configured, ticket prefix, `members_can_edit`) is memory only.
15. **Session delete** is an internal transition with the HTTP caller as `Viewer` (`DeleteSession`). After it every
    client command is `not_found`.

## Projection and the client fold (U31, U48)

The canonical order: rounds in display order; votes by round order, then pid; observers, roster and presence by pid.
Pids compare as their lower-case UUID strings, ordinally. A reducer that follows these rules reproduces the server's
snapshot and overlay exactly (`ViewerModel` in the tests is the reference; the property tests check it after every
random sequence for every viewer):

* `poker.vote.state` with `status:'empty'` removes that seat's vote (public and own). With values (it is the viewer's
  own) it sets the own entry and sets the public entry to `{status: locked ? 'locked' : 'selected'}`. With only a
  status it sets the public entry.
* `poker.round.revealed` replaces the round's votes with the revealed values (`locked:true`, `abstained`, points,
  high; no status), clears its own entries and sets state, winner, `revealedAt` and `revealedBy`.
* `poker.round.replayed` turns the round's public entries into `{status:'locked'}`; the owner-only vote states and the
  `poker.round.updated` that follow carry the rest.
* `poker.round.created` appends; `updated` replaces by id; `deleted` removes the round, its votes and its Jira submit,
  and clears `currentRoundId` when it pointed there; `order` reorders; `rounds.reset` leaves only the new round and
  clears votes, submits and the pointer; `pointer` sets `currentRoundId`.
* `poker.jira.points` with `ok` removes the round's submit entry; `pending` or `failed` replaces it.
* `heldByThisTab` cannot be derived from tx frames: the client sets it from its own take or move being acked and clears
  it when a `poker.spotlight` names someone else. The transcripts never end with the viewer's own tab holding it.

**Navigation (`navTarget`, R13).** Per tx frame, in event order: `poker.pointer` with `nav:true` targets its round
for everyone, followers of someone else's spotlight included; a `poker.spotlight` whose round differs from the
previous spotlight round targets it when follow is on and the holder is someone else. A target that no longer exists
at the end of the frame is dropped. If the viewer's round (after the target) no longer exists, the target is the
pointer round. `expectedNav[0]` is the round a joiner lands on: the spotlight round when following someone else's
spotlight, else the pointer round. Each later entry is the frame's target, or null for no navigation (a target equal
to the current round is still reported).

**Transcript files** (`tests/golden/transcripts/poker-*.json`): `{name, description, viewer:{pid,cid}, frames,
expectedNav, expectedViewerState:{d,o}}`. `frames` are server frames exactly as `WireWriter` writes them: a `snap` at
seq 0, then one `tx` per transition that reaches the wire (memory-only transitions emit none). The frames carry no
presence events: presence is the runtime's, and it does not change during a transcript. `TranscriptTests` regenerates
a stale file and fails; commit the regenerated file.

## Verification

* `dotnet test tests/Retroscope.Core.Tests --filter Category=Poker`: 114 tests, including all 10,000 golden scoring
  vectors and two FsCheck properties (300 team and 200 quick sequences of up to 120 operations from six principals and
  a second tab, with joins, disconnects, time passing and Jira results). After every step: §b invariants (unique
  numbers, dense order, pointer and spotlight on existing rounds, pending ⇔ owner, no unlocked vote on a revealed
  round, no observer vote on a voting round, valid keys and votes), `Decide` leaves the state untouched, an accepted
  client command redelivered is not accepted again (except a create that only filled the placeholder, see 8), and no
  frame or snapshot shows another principal's values while their round is voting. At the end every viewer's fold
  equals a fresh snapshot.
* A one-off soak at 3,000 tests per property with sequences up to 200 operations passed.
* Injected bugs were caught: projecting a vote's values to every viewer (secrecy), and skipping the spotlight repair
  on round removal (invariants).
