# U20 decisions: blobs

U20 owns `Server/Endpoints/BlobEndpoints.cs`, `Server/Data/Repos/BlobsRepo.cs`, `Server/Json/BlobJsonContext.cs`
(transferred per U0 decision 3) and its tests in `tests/Retroscope.Integration.Tests/Blobs/**`.

## Contracts later units rely on

| Type | Use |
|---|---|
| `ImageSniffer.Detect(bytes)` | PNG, JPEG, GIF or WebP by magic bytes **and** container structure; null otherwise |
| `SniffedImage.TryCreate(bytes, out image)` | The only way to get bytes `BlobsRepo` will store; carries the sniffed type and sha256 |
| `BlobsRepo.InsertAvatarAsync(id, by, image, ct)` | U16 (`PUT /api/me/avatar`) and U18 (Google picture). Throws above 256 KiB. Setting `users.avatar_blob_id` and deleting the old avatar stay with them |
| `BlobsRepo.InsertBoardImageAsync(...)` | `Inserted`, `BoardFull` or `StoreFull`; used by the upload route |
| `BlobsRepo.DeleteUnattachedAsync(createdBefore, limit, ct)` | U27's GC job: pass `now - BlobsRepo.UnattachedTtl` (24 h) and loop while it returns `limit` |
| `BlobsRepo.BoardImageBytesAsync(ct)` | "blob bytes" for `/api/admin/stats` (U27) |
| `BlobEndpoints.BlobContentSecurityPolicy` | `default-src 'none'; sandbox` |

## Decisions where the spec was silent or did not fit

1. **Sniffing walks the whole container.** A magic-byte prefix alone accepts a polyglot (an image with HTML,
   script or a zip appended, or a signature in front of markup). The sniffer walks PNG chunks (IHDR first, an IDAT,
   IEND last), JPEG segments and entropy-coded data up to EOI, GIF blocks up to the trailer, and WebP RIFF chunks
   (the RIFF size must equal the file), and requires the container to end exactly at the last byte. CRCs and
   codec payloads are not checked: that would not stop a payload hidden inside a comment segment, and the response
   headers (`nosniff`, the declared image type, `sandbox` CSP) already keep such bytes inert. The declared
   `Content-Type` of the upload is ignored; the stored type is the sniffed one. GIF is accepted because §b allows it.
2. **Types live in the two owned files.** `ImageSniffer`, `SniffedImage`, `BlobOptions`, `BlobCreated` and
   `BlobLog` sit in `BlobEndpoints.cs`; `BlobPurpose`, `BoardImageInsert`, `StoredBlob`, `BoardView` and the
   caller access view in `BlobsRepo.cs`, because U20 owns no other file.
3. **Board access is read from the database with the blob.** One query returns the board facts, the caller's
   `team_members.role` and `board_access_grants.password_epoch`, wrapped as an `IAccessView` for that one caller,
   and `Policy.Can` decides. The team and board actors commit membership and grants before announcing them, so
   the row is never behind them, and no actor or membership cache has to be loaded to serve an image. A grant is
   current when its `password_epoch` equals the board's `password_set_at`.
4. **Who may read a board image** is `Policy.Can(Subscribe)` on its board: deleted boards and boards of deleted
   teams are refused, archived boards are readable. A refused image answers exactly like a missing blob (404
   `not_found`, same headers and body, tested), so ids reveal nothing.
5. **Who may upload.** Route policy `BoardAccess`. Order: no access → 404 `not_found` (as above); archived → 403
   `board_archived`; `Policy.Can(RetroAddCard)` false → 403 `forbidden`; stage → 403 `stage_forbids`. "Stage allows
   adding" means some column takes new content now: stages off, `thinking`, or `discussing` when the board has an
   action-items column (the gate of `StageRules.AllowsContent` for any column). The image is not tied to a column.
6. **Status codes.** Body over 2 MiB → 413 `too_large` (checked from `Content-Length` before reading, and again
   while reading). Not an accepted image → 415 `unsupported_media_type`. Board over its 50 MiB → **409
   `board_quota`** (the spec names no code). Global ceiling → 507 `storage_full` and an `Error` log naming
   `BLOB_BYTES_MAX`. Success → **201** `{blobId}`.
7. **Quota and ceiling are checked inside the insert statement**, one round trip: a CTE sums board-image sizes for
   the board and overall and inserts only if both stay within bounds. Uploads racing each other can overshoot by
   at most their own sizes (≤ 2 MiB each); a lock per upload was not worth it. The ceiling counts board images
   only (avatars are capped per row at 256 KiB and are one per user). The sum reads only `byte_size`; the bytes
   column is `storage external`, so it does not touch the image data.
8. **Rate limits.** Upload: 30/h per principal and 60/h per IP (§d). Every attempt counts, refused ones included,
   because the limiter runs before the handler. `GET /blob/{id}` is `Public` with 600/min per IP and per principal:
   generous because a board can show many images, and responses are cached for a year anyway.
9. **Cache headers.** Avatars `public, max-age=31536000, immutable`; board images `private, max-age=31536000,
   immutable`. §d wrote "avatars `public, immutable`"; `immutable` means nothing without a `max-age`, and a blob's
   bytes never change under its id (a new avatar is a new blob). Revoked board access does not purge a browser's
   private cache; that is inherent to the §d header and accepted.
10. **Blob ids are random v4 GUIDs**, not v7: avatars are public by id, so ids should not be enumerable or leak
    upload times.
11. **`BLOB_BYTES_MAX`** must be a positive integer number of bytes; anything else fails startup. Unset means
    2 GiB.

## Tests

`dotnet test tests/Retroscope.Integration.Tests --filter Category=Blobs`: 51 tests. Fixtures are real encoder
output (Pillow 12.1: PNG, baseline and progressive JPEG, GIF87a and animated GIF89a, lossy/VP8X, lossless and
animated WebP). Every proper prefix and every suffix-extended variant of each fixture is refused. The GC test
checks that the query uses `blobs_unattached_ix`.

## Follow-ups for other units

- **U16:** `PUT /api/me/avatar` reads the body (≤ 256 KiB), calls `SniffedImage.TryCreate` and
  `BlobsRepo.InsertAvatarAsync`, then points `users.avatar_blob_id` at it; answer 415 `unsupported_media_type` for
  a refused image, as the board upload does.
- **U18:** store the fetched Google picture through the same two calls.
- **U22:** the attach `update` is scoped `where board_id = $board and purpose = 'board_image'` (U8 decision 10);
  for an anonymous card or comment it also sets `created_by = null` (S6).
- **U27:** run `DeleteUnattachedAsync(now - BlobsRepo.UnattachedTtl, batch)` from the retention job; report
  `BoardImageBytesAsync` as blob bytes in `/api/admin/stats`.
- **U34 / U36 (front end):** post the raw file bytes as the request body (any `Content-Type`), with `X-RS: 1`;
  read `blobId` from the 201 body and map 409 `board_quota`, 413, 415 and 507 to messages.
