# UF12: team, membership, jobs and Jira correctness

Spec: `docs/followups/UF12.md`. Amendments to U23, U24, U26 and U27 point back here.

## Contracts later units rely on

| Type / route | Use |
|---|---|
| `TeamInput.TransferOwnership(Owner, NewOwner)` | One ask: `Owner` (must hold the role in the team actor's state) becomes admin and `NewOwner` (a member) becomes owner, as one `TeamEvent.OwnershipTransferred` committed in one transaction. Rejects `invalid` (same principal), `not_found` (not a member), `forbidden` (`Owner` is not the owner); a retry after the transfer committed is a no-op. The wire form is `team.members` with the whole roster |
| `DELETE /api/teams/{teamId}/jira/issues/{key}/links/{linkId}` | Replaces `DELETE …/jira/links/{linkId}`. 404 `jira_not_found` unless the issue's own link list (read from Jira, not the cache) holds that link id; Jira is not called then |
| `ScheduledJob.FencedAsync(dataSource, leader, ct, statements…)` | Runs a delete batch as one transaction behind `rs_fence` (`Leader.CommitFencedAsync`) and returns the first statement's row count. Throws `FencingLostException` once leadership is lost |
| `FakeJql` / `FakeJiraServer` | FakeJira evaluates the JQL subset the app sends (below), answers searches and the Agile sprint/backlog pages (their `jql` parameter included) in rank order, and stores issue links. `AddIssue(…, status, issueType)`, `RankFirst(key)`, `LinkIds` |
| `recent_activity_entity_ix` | `db/migrations/0002_recent_activity_entity_ix.sql`: `(entity_kind, entity_id)` |

## Decisions where the spec was silent or did not fit

1. **Soft-deleted teams have no members.** `MembershipCache`'s member query joins `teams` and requires
   `deleted_at is null`, for `LoadAsync` and for the synchronous `RoleIn` fallback alike. The rows in `team_members`
   stay until the team purge, so nothing else changes: an empty role set is what the delete handler already
   published (U24 decision 10), and now a restart or a `Forget` reads the same thing back.
2. **Transfer as one event.** One event with the final roster, instead of two `MemberRoleSet` events in one decision,
   so subscribers get one `team.members` frame and never see an ownerless roster. `TeamStore` writes it as two
   statements in the actor's single fenced transaction, the demotion first (`team_members_one_owner_uq` is not
   deferrable); the demotion is guarded with `role = 'owner'`. `TeamsEndpoints.TransferAsync` makes one ask and no
   longer restores anything; a `not_found` rejection (the target left meanwhile) is a 404 and any other rejection
   the usual 409 `conflict`. The audit row is written only when the ask was accepted.
3. **Link delete is scoped by the route's issue.** The route now names the issue. Before deleting, the handler drops
   the issue's cached detail and reads it again, so a link created in Jira a moment ago can still be deleted and a
   link id the issue does not list (another team's or project's link, or a guess) is 404 without calling Jira.
   Either side of a link may delete it (Jira lists the link on both issues). Afterwards both issues' cache tags are
   dropped and the rooms' Jira metadata invalidated, instead of every cached drawer of the team.
4. **FakeJira's JQL subset.** `AND`, `OR`, parentheses; `project`, `key`, `issuetype` (names and
   `subtaskIssueTypes()`), `status`, `statusCategory` (name or key), `sprint` (ids, names, `openSprints()`,
   `futureSprints()`, `closedSprints()`, `EMPTY`), `summary ~` (every word, case-insensitive) and `cf[NNNNN]` (`=`
   a number, `is [not] EMPTY`); operators `=`, `!=`, `~`, `in`, `not in`, `is [not] EMPTY`; then `ORDER BY Rank ASC`.
   As in Jira, `!=` and `not in` never match an empty field. Anything else is answered 400 ("Error in the JQL
   Query"), so a query the app starts sending outside the subset fails loudly. Issues rank in creation order unless
   `RankFirst` moves one. A search without `ORDER BY` keeps the old key order. The status category now follows
   Jira's three categories ("In Progress"/"In Review" are In Progress); before, every non-Done status was `new`.
5. **The fence covers every delete batch** of retention (each quick room, the cursor sweep, each blob batch, dead
   mail, audit) and of the team purge (each team). `Leader.CommitFencedAsync` runs batches with `ExecuteNonQuery`,
   where a `select` reports no row count, so the purge statements count through a data-modifying main statement:
   a quick room is three statements in one transaction (the room delete, which counts, then its cursors and
   recent-activity rows only if the room is gone), and the team purge's main statement is its `team.purge` audit
   insert, one row per team deleted. The blob batch reuses `BlobsRepo.DeleteUnattachedSql`;
   `BlobsRepo.DeleteUnattachedAsync` is left in place for U20. The token sweep is not fenced: it deletes credentials
   that are already expired, which no actor writes, and the spec names retention and the team purge.
6. **Paging.** Candidates are listed in `(last_activity_at, id)` (rooms) or `(deleted_at, id)` (teams) keyset order,
   `PageSize` at a time (500 and 100), until a short page or the per-pass cap (500 rooms per kind, 100 teams)
   counted in rooms actually purged. Skipped rooms no longer use up the pass. `PageSize` is an `internal init`
   property so tests can page with two or three rows.
7. **Indexed purge lookups.** The team purge matches `recent_activity` with `(entity_kind, entity_id) in (…)` and
   `client_cursors` with `room_key in (…)` (its primary key leads with `room_key`). `recent_activity`'s primary key
   leads with `user_id`, so 0002 adds `recent_activity_entity_ix`; the quick-room retention statements use it as well.
   `TeamPurgeJob.PurgeSql` is `internal` so the plan test can `EXPLAIN` the real statement. 0001 is unchanged.
8. **Spot load in the importer tests** runs `SpotLoadCommand.RunAsync(services, …)` over a small service collection
   (the data source over the app role, the started leader, the real stores), and checks the report and the summary
   line; the stores no longer appear in the test. The command samples only rooms that should open (not deleted, not
   of a soft-deleted team), which for this import is every room.

9. **Edits outside the owned paths that 0002 forces.** Adding a second migration broke two U1 schema tests that
   probed with a hand-made "version 2" on a database the embedded migrator had fully migrated; they now migrate only
   0001 first and probe above it, which keeps what they prove. `tests/schema.snapshot.sql` was regenerated with
   `RS_UPDATE_SCHEMA_SNAPSHOT=1` and differs only by the new index. FakeJira numbers links from 10001, as the U19 client
   test that deletes link 10001 after creating one expects (the fake now refuses unknown link ids, as Jira does).

## Follow-ups for other units

- **UF14 (web) / integrator:** the issue drawer must call `DELETE ${base}/issues/${key}/links/${id}`
  (`web/src/poker/issue-drawer.js`, the "Remove link" button), and `tests/web-fake-server/jira.js`,
  `tests/web-fake-server/self.test.js` and `tests/e2e/fake/poker-jira/drawer.spec.js` should move to the same route.
  Until then removing a link from the drawer gets a 404 from the real server; the fake e2e suite is unaffected.
- **Owner of `AdminEndpoints` (U27's file) / integrator:** the admin membership repair still makes someone owner with
  two asks (demote the current owner, then promote). It should ask `TeamInput.TransferOwnership` when the user is
  already a member, and add the user as a member first otherwise, so a failure never leaves the team without an
  owner.
- **DESIGN §d** still lists `DELETE links/{id}` among the Jira routes; it is `DELETE issues/{key}/links/{id}`.
