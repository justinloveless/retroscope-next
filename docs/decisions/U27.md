# U27 decisions: admin and jobs

U27 owns `Server/Endpoints/AdminEndpoints.cs`, `Server/Jobs/{RetentionJob,TokenSweepJob,TeamPurgeJob}.cs`,
`Server/Hosting/SpotLoadCommand.cs`, `Server/Json/AdminJsonContext.cs` (U0 decision 3) and, following the U13/U14
precedent, its tests in `tests/Retroscope.Integration.Tests/Admin/**` (`Category=Admin`).

## Contracts other units rely on

| Type / route | Use |
|---|---|
| `GET /api/admin/users?q=` | `[{id, name, email (masked), isAdmin, disabled}]`, at most 50. `q` is a case-insensitive prefix of the email, full name or nickname; empty lists the first 50 by email |
| `PATCH /api/admin/users/{id}` | `{disabled?, isAdmin?}` → the same user object. 409 `last_admin`, 404 `not_found`, 400 `invalid` when neither member is given |
| `GET /api/admin/teams?q=` | `[{id, name, memberCount}]`, not-deleted teams whose name contains `q` |
| `POST /api/admin/teams/{id}/members` | `{userId, role?}` (`member` by default, `admin` or `owner`) → 204. 404 for an unknown or deleted team or unknown user, 409 `owner_required` |
| `DELETE /api/admin/teams/{id}/members/{userId}` | 204, also when the user was not a member; 409 `owner_required` for the owner |
| `GET /api/admin/stats` | `{uptimeSeconds, rssBytes, managedHeapBytes, liveRooms, sockets, poolSize, poolOpen, poolInUse, ringBytes, blobBytes, emailBudgetDrops, outboxDepth}` |
| `RetentionJob.RunAsync`, `TokenSweepJob.RunAsync`, `TeamPurgeJob.RunAsync` | One pass each, returning a report; the hosted loop calls them hourly |
| `SpotLoadCommand.RunAsync(services, sample, output, ct)` | The in-process spot-load U42's end-to-end test can call; `RunAsync(app, args)` is the subcommand |

## Decisions where the spec was silent or did not fit

1. **Where "last admin" applies.** §d says "cannot demote the last admin". Disabling the last admin locks everyone out
   just as surely, so the rule is: after the change at least one admin who is not disabled must remain. A disabled admin
   does not count. Changes to admin flags are serialized with a transaction-scoped advisory lock (`0x52534144`), so two
   admins demoting each other at the same moment cannot both succeed; a row lock on the target alone would allow it
   (tested by removing the lock).
2. **What a privilege change does.** As the carried follow-up asks, disabling a user and changing `is_admin` both call
   `Sessions.RevokeAllAsync` (every session deleted and its sockets closed with 4401), `IConnectionRevoker.RevokePrincipal`
   for every registered revoker, and `Sessions.EvictUser`. A promoted user signs in again and the new session carries
   the admin flag; an admin who demotes themselves signs themselves out. Re-enabling only evicts the cache.
3. **Audit actions.** `admin.user.disable`, `admin.user.enable`, `admin.user.grant_admin`, `admin.user.revoke_admin`
   (target: the user id) are written in the same transaction as the change. Membership repair writes
   `admin.team.member.add`, `admin.team.member.role` and `admin.team.member.remove` with `team_id` and `meta.role`,
   after the team actor accepted the change (an actor commit cannot carry a row from the handler). The team purge writes
   `team.purge` with no actor. The `auth.signup` and `auth.signup.taken` rows (UF7) need nothing from the admin API; there
   is no audit viewer in §d.
4. **Membership repair keeps one owner.** Every change is an `AskAsync` to the team actor (R24), so the cache, the
   roster and the team's live rooms follow. Making someone owner first demotes the current owner to admin (the one-owner
   index is not deferrable), then adds or promotes the user. Demoting or removing the owner is refused with
   `owner_required`: set another owner instead. A team with no owner at all (an import repair, U42) can be given one.
   Member names follow `TeamStore`'s roster rule (nickname, full name, `User`), so a member added here equals the same
   member loaded from the rows.
5. **Pool statistics.** Npgsql 10 has no public pool counters (its XML docs list no statistics member on
   `NpgsqlDataSource`). `poolOpen` and `poolInUse` count the app role's backends in this database from
   `pg_stat_activity` (busy ones exclude the query's own backend); `poolSize` is `Max Pool Size` from the data source's
   connection string. The lease connection runs as the owner and is not counted.
6. **Job scheduling.** The three jobs share a `ScheduledJob` base (a `BackgroundService` in `RetentionJob.cs`, since U27
   owns no other file in `Jobs/`): first pass one minute after start, then hourly, only while this instance is leader
   (or when no `ILeaderEpoch` is registered, as in test hosts). The delays use the injected `TimeProvider`, so hosts on a
   fake clock (every integration test) never run a pass by themselves; the route inventory's real host stops long before
   the first minute. They are registered from `AdminEndpoints.AddServices` (U0 decision 2) as singletons, so tests and
   tools can resolve them and call `RunAsync`.
7. **Retention details.**
   * Quick sessions and boards idle for 30 days go through `ActorRegistry.TryPurgeAsync`, one room at a time. The delete
     repeats the idle test in SQL and removes the room's `client_cursors` and `recent_activity` rows in the same
     statement (neither has a foreign key). A room with a subscriber is skipped and retried next hour. At most 500 rooms
     per kind per pass.
   * Cursors: `updated_on` more than 14 days before today (UTC, from the clock). Board images: `BlobsRepo.DeleteUnattachedAsync`
     in batches of 200 until a batch comes back short. Dead mail: `body_text is null` and `created_at` over 7 days ago.
     Audit rows over 180 days old.
8. **Token sweep.** Sessions past either expiry, guest tokens and auth tokens past `expires_at` (consumed or not), and
   team invites that are revoked or past `expires_at`. Swept sessions are passed to `Sessions.Revoked`, so a socket still
   authenticated by an expired session closes and the cache forgets it. Guest principals stay: they author content.
9. **Team purge.** Teams soft-deleted more than 30 days ago are deleted in one statement under the team room's key
   (`TryPurgeAsync`); cascades take sessions, boards, images, members, invites and Jira settings, and the statement also
   deletes the cursors and recent-activity rows of the team room and every session and board of the team. The team's
   poker and board keys are not held: a room of a soft-deleted team loads as missing (U21 decision 9, U22 decision 10),
   so a racing load neither shows nor writes anything. The membership cache entry is dropped afterwards.
10. **spot-load.**
    * It takes the leader lease when the process does not hold it, because `TeamStore.LoadAsync` runs its repair
      statement under the epoch fence. That also means it must run with the app stopped, which is when §h.6 runs it
      (after `pg_restore`, before `cutover`); against a running app it exits 1 after `LEADER_ACQUIRE_SECONDS` with
      "Stop the app before running spot-load".
    * It samples with `order by random()` only rooms that should open: not deleted, and not of a soft-deleted team.
    * Each room is loaded through the real store and turned into the `snap` frame an anonymous guest viewer would get
      (shared snapshot of the non-member variant plus the overlay, through the real bindings), and the frame must parse
      back with `WireParser.ParseServer`. It loads directly, not through actors: an actor would start the poker room's
      Jira metadata loop and timers. `RetroStore` is constructed with no team notices (it is not registered in DI).
    * Output: one `FAIL <room>: <error>` line per failure and a summary `spot-load: poker N, board N, team N loaded; F
      failed`. Exit 0 when all loaded, 1 otherwise, 2 for bad arguments (`--sample` must be 1–10000).

## Verification

- `dotnet test tests/Retroscope.Integration.Tests --filter Category=Admin`: 30 tests pass. They cover the route policy,
  search and masking, last-admin protection (including two admins demoting each other concurrently, five rounds),
  disable revoking sessions and closing a real socket with 4401, admin grants, audit rows, membership repair through
  the team actor (owner transfer, refusals, the live roster), stats, retention of each kind, a purge racing a load held
  open with a row lock, the token sweep, the team purge cascade, and spot-load in process and through the real binary
  (exit codes 0, 1 and 2).
- Mutations, each reverted: purging without `TryPurgeAsync` fails the skip test and the race test; dropping the
  advisory lock fails the concurrent-demotion test.

## Amendment (UF12)

1. Every retention and team-purge delete batch commits through the leader fence; a pass that finds the fence moved
   stops with `FencingLostException` (decision 7 and 9).
2. Candidates are keyset-paged, so rooms in use no longer starve the idle rooms after them; the per-pass caps count
   purged rooms and teams.
3. The team purge matches `recent_activity` by `(entity_kind, entity_id)` through `recent_activity_entity_ix`
   (migration 0002).
4. The importer's `SpotLoadTests` run `SpotLoadCommand`. Details in `docs/decisions/UF12.md`.

## Amendment (UF15)

1. Making someone the owner through `POST /api/admin/teams/{id}/members` asks `TeamInput.TransferOwnership` (one team
   actor transaction) instead of demoting the owner and then promoting the new one. Someone who is not a member yet is
   added as a member first. The audit rows are `admin.team.member.add` (when added) and `admin.team.owner.transfer`
   (target the new owner, `meta.role = owner`); there is no longer a row for the old owner's demotion. A transfer the
   decider refuses because the roster changed since it was read answers 409 `conflict`. Details in
   `docs/decisions/UF15.md`.
