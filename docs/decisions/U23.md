# U23 decisions: team room and membership cache

U23 owns `src/Retroscope.Server/Realtime/Rooms/TeamRoom.cs`, `src/Retroscope.Server/Realtime/Stores/TeamStore.cs` and
`src/Retroscope.Server/Data/Repos/MembershipCache.cs`. §k names no test path; the Check runs `Category=TeamRoom` in the
integration project, so the tests live in `tests/Retroscope.Integration.Tests/TeamRoom/**` (U13/U14 precedent).

## Public surface (for U21, U22, U24–U27)

| Type | Use |
|---|---|
| `MembershipCache` | Registered as itself, `IMembershipLookup` and `IAccessView`. `LoadAsync`/`TryGet` (versioned `TeamMembership`), `Seed` (a load: never replaces a cached version), `Publish` (the team actor's committed roster: always replaces, bumps the version), `Forget`, `RoleIn`, `HasCurrentGrant` |
| `TeamNotices` | The `ITeamNotices` implementation: each call is a `Post` of the matching `TeamInput` to the live team actor |
| `TeamBinding` | The team room on the runtime: no presence, no overlay, one snapshot variant |
| `TeamStore` | `SqlRoomStore` subclass: load (with the repair query), column-scoped plans, `RoomsAsync(team)` |
| `TeamFanOut` | The registered `IRoomStore` for team rooms: `TeamStore` plus the post-commit cache publish and fan-out |

## Decisions where the spec was silent or did not fit

1. **Post-commit work lives in a store decorator.** A committed membership change must reach the cache before any
   room decides its next message (R12), and settings must reach the team's poker and board rooms (R15c). The runtime
   has no post-commit hook and `SqlRoomStore.CommitAsync` is not virtual, so `TeamFanOut` wraps `TeamStore`: after the
   commit it publishes the new roster to the cache, then posts `AccessChanged` to the team room and to every live
   session and board of the team, `RosterChanged` to sessions, `RetroInput.MembersChanged` to boards, and the changed
   settings (`PointDescriptionsChanged` to sessions, `RetroInput.TeamSettingsChanged` to boards). A fan-out failure is
   logged, never thrown: the change committed, and rooms that missed it read it when they next load. A commit that
   throws (other than a definite rejection) while carrying a roster change drops the cached version, because the
   outcome may be unknown; the reloading actor republishes from the rows.
2. **Which rooms belong to the team** comes from one query (`poker_sessions.team_id`, `retro_boards.team_id` not
   deleted) per membership or settings change. The registry cannot enumerate live rooms (`ActorRegistry` is UF7's),
   and posts to rooms that are not live are dropped by `ActorRegistry.Post` (U13 decision 12), so nothing starts.
3. **Durability.** Events that write nothing (`ActionItemAdded`, `ActionItemSourceDetached`,
   `ActionItemCommentsCounted`, `BoardsChanged`, `PokerChanged`) are `Ephemeral`: sequenced and fanned out without an
   empty fenced transaction. `SettingsChanged` and `TeamDeleted` also write nothing (U9: the HTTP handler wrote them)
   but stay `Committed`, so they pass through the store and its fan-out.
4. **Writes.** Member events insert, update or delete `team_members` (a plain insert: a row the actor does not know
   about is a bug and nacks `internal`). Action-item updates name only their columns and are scoped to the team id;
   text sync is guarded with `source_version < $v` in SQL as well as in the decider.
5. **The repair query runs fenced at load**, as its own transaction before the load batch. It only moves copies
   forward, but it is still a write, and every write from an actor carries the fence.
6. **The team actor's load publishes** the roster it read (rather than seeding), so a reload after an unknown commit
   outcome corrects the cache. Board and poker loads (and `RoomResolver`) go through `LoadAsync`, which seeds: a
   published version is never older than the rows, so a slow load must not replace it.
7. **`RoleIn` on an unloaded team reads the rows synchronously**, once per team per process. Callers are expected to
   call `LoadAsync` first (rooms in their store's load, the resolver before its check, as U11 does); the fallback only
   keeps a caller that did not from denying a member. Nothing evicts teams: there are few, and only the team actor
   writes `team_members` (R24).
8. **Grants are cached only when current.** `HasCurrentGrant` compares the grant's `password_epoch` with the board's
   `password_set_at`. A matching epoch is cached; a miss or an older epoch reads the row again (synchronous, one
   indexed lookup), because the board actor may have granted since and no notification exists for it. The cache is
   cleared when it reaches 16,384 entries.
9. **Team snapshot.** Item comment counts are counted from `retro_comments` on the source card at load; endorsement
   types include archived ones (with `archived: true`) in `sort_key` order; point descriptions keep string values
   only. A soft-deleted team loads as missing (`not_found`); a team deleted while live is `IsDeleted` and its
   subscribers are kicked `deleted`.
10. **`TeamRoomJsonContext` keeps U0's placeholder.** Point descriptions are read with `JsonDocument`, which needs no
    generated metadata, so the room has no types to register.

## Not done here (follow-ups)

- **`IRoomGateway`.** The carried follow-up says rooms fan out through `IClientConnection.Send`, but the gateway that
  adapts connections to `IRoomPeer` serves every room kind and still does not exist (`UnavailableRoomGateway` is
  registered). It belongs with the runtime/transport (UF7 owns both this wave) or the integrator, not in one room's
  file: three parallel room units each adding one would conflict. The team room needs nothing kind-specific from it.
- **U21/U22:** load the team's membership with `IMembershipLookup.LoadAsync` in your store's `LoadAsync`, and pass
  the team's roster to the board as `MemberInfo`s (the team actor sends `RetroInput.MembersChanged` after each change).
  Your bindings' `IsMember`/`CanSubscribe` are re-run on the `AccessChanged` the team actor posts, so a member who
  drops to non-member on a link or password team board gets the non-member snapshot.
- **U24:** route invite accept, role changes, removals and admin repair through `AskAsync<TeamState, TeamInput>`
  (`MemberAdded`, `MemberRoleSet`, `MemberRemoved`): `Post` would drop the change when the team actor is not live, and
  only the actor writes `team_members`. An ownership transfer must demote the old owner before promoting the new one
  (`team_members_one_owner_uq` is not deferrable). After writing settings, ask `SettingsChanged` so the fan-out runs.
  Membership audit rows are the handler's.
- **U25/U22:** a board actor that inserts a grant need not notify the cache; the next check reads it.

## Verification

- `dotnet test tests/Retroscope.Integration.Tests --filter Category=TeamRoom`: 19 tests pass (three consecutive runs).
  Mutations checked: without the cache publish four tests fail (member added, removal kick, demotion, board variant);
  without the `source_version < $v` guard the text-sync SQL test fails.
- `./build.sh test`: see the unit report.

## Amendment (UF9)

1. A committed `TeamDeleted` publishes an empty role set and posts `AccessChanged` to the team's live sessions and
   boards.
2. Loading the team room posts the roster it read to the team's live rooms, so a member change whose commit outcome was
   unknown still reaches them.
3. `TeamRoom/RealServerTests`: two members see each other's action-item changes over real sockets, and removing a
   member kicks their live team socket.
