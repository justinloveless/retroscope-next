# UX17 decisions: the sprint report on the retro board

The owner asked for a sprint report on retro boards, so that a team can remind itself what happened in a sprint
before it talks about it. Three choices came from the owner and are fixed:

- The viewer picks the sprint. Nothing infers "the sprint since the last retro" from board dates.
- Only members of the board's team see the report. Guests, signed-in non-members on link or password boards and
  quick boards get no entry point, and the server refuses them.
- The report opens in a panel like the poker Jira browser.

The report is new: the original app had none, and DESIGN §0.1 does not list it. It revives nothing that §0.1
dropped. It adds no realtime state, no room command, no migration and no Authz capability.

UX17 adds `src/Retroscope.Core/Sprints/SprintClassifier.cs`, `src/Retroscope.Server/Jira/SprintReportService.cs`,
`src/Retroscope.Server/Endpoints/JiraEndpoints.SprintReport.cs`, `web/src/retro/{sprint,sprint-report}.js`,
`web/src/ui/side-sheet.js`, `web/src/core/jira-errors.js`, their tests, the `tests/e2e/fake/retro-sprint/` spec
and this file. It edits `JiraMap.cs`, `JiraClient.cs`, `Jql.cs`, `BrowseService.cs`, `JiraEndpoints.cs`,
`JiraHttpJsonContext.cs`, `web/src/poker/submit.js`, `web/src/retro/{actions,index}.js`, `web/styles/retro.css`,
`web/budgets.json`, `tools/quick.mjs`, FakeJira, the web fake and its fixtures, the screenshot states and
DESIGN §f, §g.1 and §g.7.

## Decisions

1. **A snapshot, not a rebuild of Jira's own sprint report.** Jira has no supported sprint-report endpoint. The
   one its UI uses (`/rest/greenhopper/1.0/rapid/charts/sprintreport`) is private and unversioned, and DESIGN §f
   limits the proxy to platform REST v3 and Agile 1.0. Rebuilding Jira's numbers from issue changelogs
   (`POST /rest/api/3/changelog/bulkfetch`) would show issues added and removed mid-sprint and estimate changes,
   but the sprint field's changelog format is not documented, removed issues cannot be found with JQL (the Sprint
   field supports neither `WAS` nor `CHANGED`), and FakeJira would need a changelog engine. The report therefore
   reads the issues whose Sprint field still holds the sprint, with one `search/jql` (`sprint = N`, no epics or
   sub-tasks, rank order, at most 10 pages of 100, `truncated` beyond). The panel's footnote says what it leaves
   out: issues removed before the close, which issues were added after the start, and estimates at the start.
   The response shape leaves room for a scope section later.
2. **Three outcomes, plus where unfinished work went.** `SprintClassifier` (Core, pure) sorts each issue into
   `done`, `doneAfter` (finished, but after the sprint closed) or `notDone`. It also flags `carriedIn` (the issue
   was in an earlier closed sprint) and, for a closed sprint, the earliest later sprint that holds the issue (the
   panel's `→ Sprint 43`), or none (`→ Backlog`, shown on unfinished issues only). "Done" is the `done` status
   category, as in browse; a team whose board's done column maps another category will see small differences
   from Jira's report. The done instant is `resolutiondate`, else `statuscategorychangedate`; without either, an
   issue that also sits in a later sprint was unfinished at the close, because closing a sprint moves only
   unfinished work. A closed sprint without `completeDate` uses `endDate`. The sealed `ReportedSprint.Active`
   and `ReportedSprint.Closed` records make "done after the close" and a destination impossible for an active
   sprint.
3. **One route, one round trip.** `GET /api/teams/{id}/jira/sprint-report?sprint=N` answers the picker and one
   sprint's report together, so opening the panel costs one request. Without `sprint` it reports the most
   recently closed sprint, else the active one. The panel remembers the viewer's last pick per retro board in
   `localStorage` (the sprint id only).
4. **The picker is the allow-list.** The picker (active sprints, then the newest 30 closed ones of the configured
   board, without sprints whose `originBoardId` names another board) is cached for 5 minutes. A report can be
   asked only for a sprint on it; any other id is 404 `jira_not_found` and never reaches Jira, so the team's token
   cannot be used to read other sprints of the site. The picker also gives each sprint's state before the report
   is built, so the report's lifetime (15 minutes closed, 60 s active) is known without a new `JiraCache` feature.
   A sprint that closes between the active and closed reads is kept as closed.
5. **Reading the newest closed sprints.** The Agile API lists closed sprints oldest first and `total` is not
   always sent. `GetRecentSprintsAsync` jumps to the tail when `total` is known and pages forward otherwise,
   keeping the newest 30, at most 30 pages. Active sprints have their own call. Poker's `GetSprintsAsync`
   (active and future) is unchanged, and its caches drop the sprint goal it never shows.
6. **Members only, with the existing gate.** The route uses `RoutePolicy.TeamMember` and
   `JiraGate.CheckAsync(…, Capability.Subscribe, needsConfig: true)`, like every Jira read. A new capability would
   have had the same rule, so `tests/authz-matrix.csv` is unchanged. The client shows the button only when the
   board's team link has joined (members only), the team has Jira configured and a board is set; hidden entries
   send no request.
7. **Fields the stored config lacks are discovered for the report.** Teams imported at cutover have no
   `sprint_field_id` or `points_field_id` until an admin saves the Jira settings again. Without the sprint field
   every unfinished issue would read `→ Backlog`. When the config lacks either id, the report discovers it from
   the cached field list (`GET /rest/api/3/field`, 6 h), with the same rules as config save. Nothing is written
   back from this read path.
8. **Dates pass through.** Sprint dates are Jira's strings, as on every other Jira route. Core works in Unix
   milliseconds parsed at the boundary.
9. **A side sheet, not poker's side panel.** Poker's `createSidePanel` is a resizable column of the poker stage,
   and its CSS is poker-only. The retro board uses the non-modal side sheet poker already uses on phones, moved to
   `ui/side-sheet.js` as `createSideSheet` (the name avoids `screens/sheet.js`). At 1024 px and wider the board
   reserves room for it, so the sheet sits beside the columns below the app header; on a phone it is full width.
   People can keep writing cards while it is open.
10. **The panel is a lazy chunk.** `retro/sprint.js` (the button, in the retro chunk) loads `retro/sprint-report.js`
    on the first open or on pointer intent. The new chunk has its own budget. Poker's Jira messages moved to
    `core/jira-errors.js` so the report can use them without importing poker; retro's create-specific messages
    stay in `retro/actions.js`. The report words `jira_not_found` for boards and sprints.
11. **Nothing from Jira is kept.** Summaries, statuses, assignees and goals live in the server's in-memory
    `JiraCache` and the panel's in-memory cache only.

## Amendments after the first release

The owner used the report in production and asked for three changes. Decisions 4 and 7 are amended by 12 and 13.

12. **Points follow the board.** The report showed no points. The likely cause, not confirmed against the team's data:
    Cloud sites often have two points fields ("Story Points" and "Story point estimate"), and discovery takes the first
    whose schema says story points, which need not be the one the board estimates with. The report now uses the field
    an admin chose in Team Settings (`points_field_overridden`), else the board's estimation field from
    `GET /rest/agile/1.0/board/{id}/configuration` (only when its type is `field` and the field is a custom field;
    cached 1 h; a failed read falls back), else the stored field, else discovery. Poker still reads and writes the stored
    field, so the two can differ for a team whose stored field is not the board's. The owner chose to change the report
    only for now (follow-up 5).
13. **The picker pages.** Long menus ran off the screen, so the bottom sprints could not be picked. The kit's popovers
    now cap their height to the room beside their anchor and scroll, and re-place themselves when their content grows
    (`ResizeObserver`), which fixes every long menu. The report's sprint menu lists the active sprints and the newest 4
    closed ones, and loads 8 more on "Load more sprints" or on scrolling into the bottom of the menu, up to the 100 the
    server caches. The route takes `sprints=K` and answers `hasMoreSprints`; a requested older sprint stretches the
    list so the menu can show it. Older sprints than the newest 100 are not reachable.
14. **Filter by person.** A Person control lists "Everyone", each assignee with their issue count, and "Unassigned". A
    choice filters every group and recounts the tiles and points in the client. It survives a sprint switch when the
    person has issues in the new sprint, and is not stored.
15. **The chunk budget** rose from 3.5 KB to 4.5 KB for the sprint menu and the person filter.

## Known gaps

- Not checked against a real Jira site: that search returns `statuscategorychangedate`, that the board sprint
  list sends `total`, and whether it lists other boards' sprints.
- No real-stack e2e spec: a closed sprint seeded into `tests/Fakes.Host` would show in every playground board.
